# 実ブラウザ検証（e2e）

- 実ブラウザ回帰検証は `bun run test:browser`。本番ビルドを生成し、専用の127.0.0.1:4175でプレビュー、インストール済みGoogle Chromeをheadless起動する。`e2e/*.e2e.ts` はVitestと分離し、型検査・Lintの対象に含める。5回の2D/3D切り替え、ステージ一巡、`WEBGL_lose_context`による喪失後の2D継続と再試行、取得保留中の解除、実時間30秒のタイムアウト、キーボードショートカット（クリック後のボタン上の`Space`、遷移中の無視）と全画面切り替えを確認する。`test-results/` はGit管理外。長時間・実機タッチ・音の実聴を検証するものではない。
- `scene-warmup.e2e.ts` は試験の初回描画の分割（`?warmup=split`）で、温め中の画質変更（やり直して新しい画質で準備完了）、庭の温め中のリサイズ（canvasの寸法は温め後まで変えない）とステージ変更（やり直して水風呂で準備完了）、本体の温め中の2D切り替えと庭の温め中の実コンテキスト喪失（2Dで継続し再試行で復帰）、30秒期限の超過（2Dへ戻り再試行で準備完了）を確かめる。時間帯は本体／庭それぞれの温め中に2回選び、両操作後も同じ準備段階にいること、完了後と水風呂への移動後に最後の選択と時間値が反映されること、同一canvas・GLB各1取得・ミュートの維持を確認する（動作抑制あり、初回表示の画素比較や自動時間帯の検証ではない）。検証ブラウザ内で `readPixels` を150ms（期限のテストは1秒）待たせ、キャッシュが温まっていても各ステップで処理を返させる（読み込み時間の計測ではない）。後回しの描画状態の有無は `scripts/diagnose_compile_batches.mjs` の条件 `w` で測る。
- `gpu-memory.e2e.ts` は `gpu-memory.ts` で検証ブラウザ内のWebGL2の確保・解放の呼び出し（`texImage*`・`texStorage*`・`bufferData`・`renderbufferStorage*`・`delete*`）をGLオブジェクトごとに数え、コンテキストごとのテクスチャ・バッファ・レンダーバッファのバイト数と描画バッファの推定値を出す（`?resolution=fixed`）。3画質で全ステージとロウリュを通して初回の確保を済ませてから（ロウリュは初回だけ蒸気の約22KBを確保する）、周回2回と2D→3Dの再生成3回の後で、同じステージ・画質の合計が一致すること、2Dへ戻した旧コンテキストが失われ（`forceContextLoss`）バッファ・レンダーバッファを残さないことを確かめる。`gpu-memory` 添付に大きい順の確保（呼び出し・寸法・内部形式）を出す。ドライバーが実際に確保する量（詰め物・内部コピー）・プログラムは含まない推定で、記録は `docs/3d-qa/gpu-memory/`。
- `audio-nodes.e2e.ts` は2D（GPU不要）で音ありで入室し、ロウリュ3回とステージ一巡を6周して、Web Audioの生成ノード数（`create*` を種類別に数える）・AudioContext数・開始して終わっていない音源数を数える。AudioContextは1つ、定位用のPanner 2つは入室時だけ、各周の生成ノード数は同じ（34）、各ステージで鳴り続ける音源はそのステージの分だけ（サウナ・水風呂1、外気浴4）であることを確かめる。`AudioBufferSourceNode` は独自の `start` を持つので両方の原型を差し替える。同じ周回を `?view=3d` でも行い、各周の終わりに3Dの準備完了を待って2D→3Dの再生成を挟む。3Dでも生成ノード数は2Dと同じで、Pannerが2つのままであること、シーンがPannerをシーン定義の `stove`・`water.spout` に置き（AudioParamは単精度なので `Math.fround` で比べる）AudioListenerをカメラへ動かしたことを確かめる。ノードの解放（GC）・音声スレッドの負荷・音の実聴の検証ではない。
- `dynamic-resolution.e2e.ts`（DPR 1.5）は、画素比rのcanvasを表示フレーム `round(4r)−3` 回に1回だけ描かせて（1.5で3回、1.25で2回、1で毎回）動的解像度が1.5→1.25→1へ下がり、外すと試行で1.25へ戻ること、画質の変更で上限へ戻ること、rAFを1フレームおき（30fps上限の模擬）にすると下げた段を戻して保留すること、`?resolution=fixed` で変わらないことを確かめる。段を下げても速くならないと制御が段下げを取り消す。画素数に比例した空回しは表示間隔の倍数に丸められ、描画自体が軽いと1.5と1.25が同じ間隔になって不安定だったため、描画の費用に依らない間引きにした。段を下げる撮影（`resolution-control.ts`）も同じ間引きを使う。制御の確認で、GPUのフレーム予算の検証ではない。
- `frame-rate.e2e.ts` は静止中の30fpsへの間引き（`src/components/3d/frameRate.ts`）を、描画したrAFの数とブラウザが出したrAFの数の比で確かめる（静止0.35〜0.65、見回し・ロウリュ中0.85超、`?frameRate=full` は静止でも0.85超）。消費電力・GPU時間の検証ではない。フレーム間隔・GPU時間を測るテスト、rAFの時刻や回数を操作するテスト、撮影するテストは `?frameRate=full` で開く（静止中に描かないフレームがあると、時刻を止めた撮影や繰り返し描画が成り立たない）。
- `temporal-aa.e2e.ts`（DPR 1.5・動作抑制）は、時間方向の蓄積（`src/components/3d/temporalAA.ts`）の静止画が `?temporal=off` の別ページと一致すること（1段階を超えて違う画素が0.001%未満。半精度の履歴が許容の外で止まった画素と、シーン自体の非数の画素）、1 CSS pxずつ12フレーム見回した後の画像は違うこと（2段階超が1%超）、軽量画質で無効になることを確かめる。ちらつきの量の検証ではない（`resolution-shimmer.visual.ts` で測る）。
- 段ごとの見た目は `bun run test:browser:visual e2e/resolution-steps.visual.ts --reporter=json`（約4分）。DPR 1.5・標準画質で18視点を1.5→1.25→1→1.5（再撮影）の順に画面の画素のPNGで撮る。段は同じ間引きで下げ、画質の変更で戻し、撮影中はrAFの時刻を止めて制御の窓を終わらせない（動作抑制なので画像は変わらない。`resolution-control.ts`）。`python3 scripts/summarize_resolution_steps.py <report.json> <出力フォルダ> <記録先>` がΔE・細部の保持率と、差の大きい窓の拡大画像を出す。記録は `docs/3d-qa/resolution-steps/`。
- 通常のブラウザ回帰はトレース（`trace: retain-on-failure`）を記録するため、描画中のページがある間に別のページで3Dを読み込むと、DevToolsの画面転送で新しいページの並列コンパイルが止まる（上限1秒の後に描き始めるまで最初のプログラムも完了せず、製品ビルドで `data-load-ms` 約6.6秒。上限なしでは約26秒）。読み込み時間を測るテストはトレースを切るか、他のページを閉じてから読み込む。切り分けは `scripts/diagnose_parallel_compile.mjs`（`docs/3d-qa/load-compile/`）。
- 検証ブラウザ（インストール済みChrome）はMetalのシェーダーキャッシュ（OSのディスク上、普段の閲覧と共用）が効いた状態で読み込むため、`data-load-ms` などの読み込み時間は2回目以降の訪問の値。キャッシュのない初回（入室時に約6〜15秒止まる）は `scripts/diagnose_other_browsers.mjs` の `SUI_COLD=1`（Chrome for Testing・WebKit）で測る（`docs/3d-qa/other-browsers/`）。
- 見回し中のちらつきは `bun run test:browser:visual e2e/resolution-shimmer.visual.ts --reporter=json`（約3分）。3ステージの既定視点×昼夕×各段で、1フレームに1 CSS px（ヨー0.004rad）ずつドラッグした13フレームを撮る。`python3 scripts/summarize_resolution_shimmer.py <report.json> <出力フォルダ> <記録先>`（SciPy必要、約2分）が回転の射影変換で前のフレームを重ね、L*の残差を画素と8 CSS px四方の面で出す（往復の補間誤差を対照、ヨーの符号も検査）。記録は `docs/3d-qa/resolution-shimmer/`。`SHIMMER_RATIOS` で段を絞り、集計の `--baseline <shimmer.json>` で別の回の同じ系列と、`--baseline-ratio` で別の回の別の段と比べる（2倍MSAAの比較は `docs/3d-qa/msaa-motion/`）。`SHIMMER_QUALITY=high` で高画質・DPR 2（段2から）を撮る（面は画質に合わせて8 CSS px）。
- 継続利用の検証は `bun run test:browser:soak`。専用の `playwright.soak.config.ts` で `e2e/*.soak.ts` のみ実行し、通常のブラウザ回帰検証から分離する。実時間5分以上、3画質・昼夕夜・ロウリュ・ステージ一巡・2D/3D再生成を繰り返し、同じステージ／画質のテクスチャ・ジオメトリ数を比較する。全計測値は `stability-samples` 添付JSONへ保存し、`--reporter=json` で取得可能。大量のtrace記録による負荷を避けるため、この設定ではtraceを無効にする。GPU総メモリ（`gpu-memory.e2e.ts`）・音声ノード数・実機性能やリーク不存在を証明する検証ではない。
- リソース比較の前には、各周回と3D再生成後に高画質で3ステージを一巡し、指定画質へ戻す。Three.jsは初めて描いた形状だけをGPUへ登録するため、水の側面像や鏡像専用の光源形状の初回確保をリークと誤認しないよう、表示履歴を揃える。蒸気も表示を終えてから比較する。数の一致条件と180フレームの標本数は維持する。遅い描画でも全周回の資源比較を終えるため待機期限30秒・全体600秒とし、添付JSONには実際の待機時間と180フレームの所要時間（平均間隔×180）、従来の15秒相当を超えた標本数を記録する。蒸気の終了待ち中にも計測は進むため、所要時間と待機時間は異なる。成功は資源数と操作継続の検証であり、FPSの性能目標達成を意味しない。
- 継続利用の停止調査は `SOAK_TIMING=1 bun run test:browser:soak --reporter=json`。`soak-timing.ts` が描画を行うrAFの100ms超の間隔・処理、Long Tasks、一部の同期WebGL呼び出し（20ms超はプログラムの `SHADER_NAME#作成順@作成時刻` 付き）と、長い描画の中で初めて使われたプログラム（`firstUsed`）を `soak-timing` 添付へ記録する（通常は無効）。`bun run test:browser:gpu e2e/quality-stall.gpu.ts --reporter=json` は高画質／軽量の切り替えだけを短く再現する（画質は準備後に適用されるので `data-quality` を待つ。画質を選んで計測・撮影するテストも同様）。`bun run test:browser:gpu e2e/load-compile.gpu.ts --reporter=json` は初回の3Dロードと2D→3Dの再生成を再現し、描画ループの外（読み込み時の最初の描画）の1ms以上の同期WebGL呼び出しも `outside` に記録する（記録は `docs/3d-qa/load-compile/`）。計測処理には追加負荷がありGPU時間・性能合格の判定ではない。記録は `docs/3d-qa/quality-stall/`。
- 各資源標本の前にUIを隠して8 CSS pxずつ12ステップ往復ドラッグし、70フレーム静止してからUIを戻す。TAAの履歴の再開・静止時の省略と、軽量画質で無効／標準・高画質で有効になることも継続利用中に通す。フレーム間隔の180フレーム窓は従来どおりステージ・画質変更からの窓であり、見回し中だけの性能計測ではない。
- 低速回線の読み込みは `bun run test:browser:network`（`playwright.network.config.ts`、`e2e/*.network.ts` のみ）。2D入室後にCDPで帯域・遅延を制限（キャッシュ・Service Worker無効）し、12 Mbps・4 Mbps・1.6 Mbpsでの準備完了（1.6 Mbpsは庭を分けた本体でのみ間に合う）と、その後の庭（`sauna-garden.glb`）の取得が本体の完了後に始まり帯域制限を受けて追加されること、0.8 Mbpsでの30秒期限切れと手動の2D切り替えによるGLB取り消し（庭は取得しない）、制限解除後の再試行を確認する。1件150秒まで。取得ごとのバイト数・時間は `network-loading` 添付JSON。プロファイルは実験用で実回線の名前ではなく、CPU制限・実機・パケット損失・本番CDNは測らない。
- 全周の目視確認用画像は `bun run test:browser:visual --reporter=json > /tmp/sauna-visual-check.json`。専用configで `e2e/*.visual.ts` のみ実行し、3ステージ×昼・夕・夜×8方向×上下・水平の216枚を `test-results/visual/` に保存する。標準画質・動作抑制・1280×800・DPR1のChrome。`python3 scripts/summarize_visual_survey.py /tmp/sauna-visual-check.json docs/3d-qa/survey`（Pillow必要）で9枚の一覧画像とモデルハッシュ付きJSONを生成する。テストの成功は撮影・操作の成功であり、画質の合格判定ではない。画質所見は進捗記録へ残す。
- 同じ実行で `e2e/cycles-compare.visual.ts` が元Cyclesのカメラ（`e2e/fixtures/cycles-cameras.json`、`scripts/blender_camera_reference.py` で元blendから生成）の位置・向き・垂直画角で撮影する。`sauna.scene.json` の取得をテスト内で差し替えるだけで、アプリにテスト用APIはない。`python3 scripts/summarize_cycles_compare.py /tmp/sauna-visual-check.json <出力先>` が `blender/renders/` と対にした比較画像を作る。照明・露出・材質は一致させていない（霧はどちらにもなく、空は同じ元blendのWorldを `sky.ts` で再現）。
- Cycles比較は `scene-capture.ts` の `rendererCaptureStyle` を screenshot の `style` に渡し、ステージのDOM演出と固定操作UIを撮影中だけ除外する。canvasのlocator screenshotにも上に重なるDOMは写るため、UI非表示・動作抑制だけでは水風呂の `.cooling-glow` の脈動を除けない。全周撮影は実際の画面演出を残す。`capture-stability.visual.ts` は03/04・昼夕について脈動の0/500msの位相では画像が異なること、演出除外後は同一ページ内の位相間でPNGが一致することを検証する。2回のページ読み込み間はテクスチャ面の孤立した十数画素が変わることがあり（影なしでも発生、原因未特定）、ブラウザで復号した変化画素0.01%以下を条件とし、割合と最大差を記録する（同一Chrome/GPU環境内の再現性）。
- `caustics.e2e.ts` は水中の疑似コースティクス（`src/components/3d/caustics.ts`）のGLSLを素のWebGL2で評価し、Blender基準値（`e2e/fixtures/blender-caustic.json`）と強度・Voronoi・ノイズを1e−4以内で照合する。続くテストは製品が読む `causticCells()` の全セルがGPUのハッシュとビット単位で一致し、キャッシュ版の模様（基準点と箱内4000点、フィルターあり・なし）がハッシュ版と完全一致することを検査する。`noise-color.e2e.ts` と同じく移植の検証で、画面の見た目の検証ではない。
- `sky.e2e.ts` は空（`src/components/3d/sky.ts`）のGLSLを素のWebGL2で、Cyclesのパノラマから取った方向（`e2e/fixtures/blender-sky.json`）で評価し、昼・夕・夜の放射輝度（1e−4＋0.1%以内）・Voronoi F1の距離と色・雲のノイズ（1e−4以内）を照合する。月の円盤（角直径0.0093rad）は参照パノラマの画素（約0.012rad）より小さく、画素中心が円盤に入ったときだけ検査される。flatな可変値は微分が0なので、画素フィルターなしの元のグラフになる。空の入口 `sui_sky` にglTF軸で渡し、軸の変換も確かめる。日光の円盤の縁・星の半径・星の密度のしきい値上の点は除く。fixtureと `sky.json` のblendのハッシュ一致も検査する。
- GPU時間は `bun run test:browser:gpu`（`playwright.gpu.config.ts`、`e2e/*.gpu.ts` のみ）。`EXT_disjoint_timer_query_webgl2` で各アニメーションフレームのコールバック全体（鏡像・影・主パス・トーンマッピング）を計測し、既定の視点とCyclesカメラ03で、サウナ・水風呂×昼夕夜の8秒間の10/50/90百分位と描画数を `gpu-time` 添付JSONへ保存する。拡張がない環境ではskip。同じ機械・ブラウザでの変更前後の相対比較用（変更前はHEADのworktreeで同じテストを実行）で、他の端末のフレーム予算ではない。`gpu-timer.ts` はWebGLのdraw呼び出しがないコールバックを除く（2026-09-28修正）。以前の集計はUIの空コールバックを含む可能性があり、新しい測定値と直接比較しない。**ANGLE Metalのタイマーは、表示間隔に収まらないフレームで実際のフレーム間隔の約1.8倍を返し、収まるフレームでは間隔の上限に隠れる**（2026-10-01、`docs/3d-qa/frame-interval/`）。予算をまたぐ変更のタイマー比は誇張されるので、`frame-cost.gpu.ts` の繰り返し描画（下記）のフレーム間隔で測る。
- 影の費用の切り分けは `bun run test:browser:gpu e2e/shadow-cost.gpu.ts --reporter=json`。高画質・1280×800・DPR1・動作抑制・庭の準備完了後、3ステージ×昼夕を通常PCSS（16+24標本）／半分（8+12）／硬い影（1参照）で測り、逆順でも繰り返す。`shaderSource` の差し替えは検証ブラウザ内だけで、製品の光源・影マップ・描画コードは変えない。共通の `gpu-timer.ts` でWebGL描画のあるコールバックだけを各条件4秒測り、1秒のクエリ回収待ち後に `shadow-cost` 添付JSONへ記録する。CPU負荷を伴う別の検証と同時に実行しない。硬い影は費用の下限を探る診断で、画質を保った最適化や60fps達成の検証ではない。差し替えは `shadow-variants.ts`（標本数で指定し、製品の定数は `softShadows.ts` から読む。置換はPCSSの関数内だけ）。
