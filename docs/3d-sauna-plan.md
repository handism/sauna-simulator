# SUI × ブラウザサウナ：3D体験の実装計画

作成日：2026-09-22  
状態：フェーズ1〜3の試験実装を進行中。GLB変換、3ステージの3D視点、遷移統合を実装。完了条件の残件・計測は [進捗記録](3d-sauna-progress.md) を参照。

## 1. 目的

このリポジトリの `blender/` にコピーされたSUIの建築・庭・素材を活用し、ブラウザで「同じ施設のサウナ、水風呂、外気浴を巡り、座って過ごす」3D体験を作る。

最初の到達点は、**質感のよいサウナ室に座り、見回し、既存の音を聞きながらロウリュできること**。この段階で画質と動作負荷を確認してから施設全体へ展開する。

完成画像の印象を重視するが、Cyclesの描画結果をそのままリアルタイムで再現できるとは想定しない。ブラウザ向けの材質調整、軽量化、演出の再構築を行う。

リポジトリのコマンド・アーキテクチャ・規約の正本は [`.claude/CLAUDE.md`](../.claude/CLAUDE.md)。本書は今後の実装計画であり、現在の実装仕様を置き換えるものではない。

## 2. 採用方針と保留事項

| 項目 | 方針 |
| --- | --- |
| 描画 | Three.jsによるリアルタイム3D。React Three Fiberの採用か直接ラップするかは初期検証時に決定する |
| 元データ | `blender/scene/SUI_Retreat.blend` を入力とする。別リポジトリの絶対パスへ依存しない。ただし `blender/` はGit管理外とする（§3「元データの管理」） |
| 配信 | 書き出したGLBとテクスチャは `public/models/` にコミットし、既存のGitHub Pagesデプロイに同梱する。Blenderの実行をCIには持ち込まない |
| 公開制御 | 3D層はフラグで明示的に有効化する。`main` への統合が即公開につながるため、既定では2D体験のまま変化しない状態を保つ |
| 既定モード | 初期リリースは2Dを既定とし、3Dはオプトイン。既定を3Dへ変えるかはフェーズ5の計測後に判断する |
| 操作 | ステージ連動の着席視点と、マウスドラッグ／タッチスワイプによる見回し |
| 移動 | 初期版はフェードで切り替える。カメラの連続移動は安全な経路を確認してから追加する |
| 質感・照明 | PBR、環境光、必要な動的照明を基本とし、間接光や陰影のベイクも検討する |
| 時間帯 | 昼／夕暮れ／自動。自動ではステージに合わせて変化させる。実装は後半に行う |
| 効果 | ロウリュの蒸気、水面波紋、控えめな呼吸・ブルーム演出 |
| 音響 | 現在のプロシージャル音源とAudioContextを活用し、位置のある音へ空間音響を追加する。`AudioEngine` の公開インターフェース変更を伴う（§4「音響」） |
| 互換性 | 3D／2D切り替え。読み込み中・失敗・非対応時には2Dで体験を継続できる |
| 初期対象外 | 自由歩行、衝突判定を伴う探索、VR、本格的な流体シミュレーション |

自由歩行、サブカメラ切り替え、レンズの曇りは将来の拡張候補とする。初期段階では、着席時の景色・音・操作感を優先する。

## 3. 既存資産の活用と注意点

### アプリ

以下は計画作成時の調査内容。実装後の変更点は進捗記録とCLAUDE.mdを参照。

- セッション進行、タイマー、心拍の演出、音、UI非表示機能を活用する。
- 現在の背景表示を3D表示層へ拡張し、既存の2D体験も維持する。
- 現在の共有 `loylyCount` は退室時に更新される（`SaunaRoom` 内の `loylyCountRef` を保持し、`completeSauna` で初めて共有状態へ渡す）。リアルタイムの蒸気発生には、押下時の専用通知が必要。
- ロウリュ通知の経路は、CLAUDE.mdの規約「コンポーネントはcontextを直接参照せず、`App.tsx` がpropsで渡す」に沿って、`SaunaRoom` へ渡すコールバックを増やす形で実装する。規約を変える場合はCLAUDE.md側も同時に更新する。
- 現在のステージ遷移には1秒のタイマーが2系統ある。`changeStage`（`useSaunaSession.ts`）が `setStage` を1秒後に実行し、`App.tsx` の `activeLayers` 用タイマーが背景レイヤーの解放を別途1秒後に行う。加えて `playAmbient` は遷移の開始時点で即座に呼ばれる。
- 3D層を足すと同種のタイマーが3系統になる。遷移の開始・完了を単一の状態として扱い、UI・音・背景・カメラがそこから派生するようにまとめる。二重遷移や時間のずれを防ぐ。

### 元データの管理

- `blender/` は約1.1GB（`scene/` 800MB、`renders/` 314MB、`assets/` 39MB）で、50MBを超えるファイルが7つある。現在Gitには追跡されていない。
- この規模をGitやGit LFSへ載せる利点は小さいため、`blender/` はGit管理外を維持する。`.gitignore` に明示し、`*.blend1` と `.DS_Store` も併せて除外する。
- 代わりに、入力とした `.blend` のファイル名・更新日時・ハッシュを書き出し記録に残し、どのシーンから生成したGLBかを追跡できるようにする。
- 結果として、クリーンクローンからの再書き出しには `.blend` の再配置が必要になる。書き出し処理の再実行手順に、この前提と入手方法を明記する。
- Gitに載せるのは書き出し後のWeb用データ（GLB・テクスチャ）のみとする。中間バージョン（`SUI_Retreat_v1`〜`v10`）はWeb用途では扱わない。

### Blender

- 建物、ベンチ、ストーブ、椅子、主要な庭要素を再利用する。
- 木・石・布の画像素材を活用し、Web用の材質へ調整する。
- プロシージャルな木目・濡れ・水・蒸気は、ベイクまたはブラウザ側の表現へ置き換える。
- 既存カメラは撮影用の構図として参考にする。ベンチに座る、水に浸かる、椅子にもたれる体験用視点を別途設定する。
- 360度見回す場合は、元のレンダリングに写っていない背面や天井も確認する。

## 4. 構成案

```text
blender/scene/SUI_Retreat.blend（Git管理外）
  → scripts/export_web_glb.py（Git管理する書き出し処理）
  → public/models/ 配下のGLBとシーン定義（Gitに追跡）
  → src/components/3d/ 配下の表示・視点・効果

既存セッション／UI
  → ステージ・ロウリュ通知・表示設定
  → 3D表示層

既存AudioContext
  ← カメラの位置・向きと音源位置
```

パスと責務は案であり、ファイル分割は採用するReactとの接続方式に合わせて決める。

### 書き出し

- 元の `.blend` を上書きせず、Web用に加工したデータを出力する。
- 初期はサウナ室と窓外の景色を抽出し、後に施設全体へ拡張する。
- カメラ、ストーブ、注水口、水面などに安定した識別名を付け、座標・向き・単位をシーン定義に出力する。
- BlenderとWebの座標系変換は書き出し時に整理し、モデルと別出力の座標が一致することを確認する。
- 元シーンのハッシュ、書き出し条件、使用素材、サイズ、形状数などを記録し、再生成できるようにする。
- 圧縮（Draco・KTX2等）の採否はフェーズ5の計測後に決めるが、後から差し込めるよう受け口だけをフェーズ1の書き出し処理に用意する。採否を後から決めるために書き出し処理を作り直すことは避ける。
- 素材の出典・ライセンス表示を確認し、配布物に必要なクレジットを含める。テクスチャは `.blend` にパック済みでGLBへ焼き込まれるため、`blender/assets/textures/CREDITS.md` の内容をWebアプリ側のクレジット表示にも反映する。

### 配信とデプロイ

- `main` への push は GitHub Pages への本番デプロイを直接起動する。未完成の3D層がそのまま公開されないよう、フラグで無効化した状態でマージできる構成にする。
- フラグはURLクエリ等の明示的な指定で有効化し、選択を保存する。既定値は2Dのままとする。
- GLBは `public/models/` に置き、`vite build` の出力へ含める。再書き出しのたびにバイナリがGitへ積み上がるため、コミットするのは各フェーズの確定版に限る。
- 転送量と保存量は GitHub Pages の制限（サイト容量、帯域）を前提に見積もる。上限に近づく場合は、外部ホスティングからの取得へ切り替える案を再検討する。

### 表示と操作

- 3D表示の読み込みは遅延実行し、2D利用時の初期負荷を抑える。現在の依存はReactとReactDOMのみで初期JSが小さいため、Three.js等が2D利用時のバンドルへ載らないことを明示的に確認する。
- 見回しは水平回転と、自然な範囲に制限した上下回転を基本にする。
- UIのタップと見回し操作を分離し、モバイルでもボタンを確実に操作できるようにする。
- UI非表示時も表示復帰の操作を残す。
- カメラ移動・慣性・呼吸による揺れは控えめにし、動きを減らす設定に対応する。
- フレームごとのカメラ・効果更新は描画側で扱い、Reactの共有状態を毎フレーム更新しない。

### セッションと効果

- ロウリュ押下を一度だけ通知する経路を作り、音と蒸気に同じ操作を伝える。
- ステージ遷移や2D／3D切り替えで、古いロウリュ通知が再生されないようにする。
- 3Dのロード状態とユーザーのモード選択を分け、読み込み完了によって選択を勝手に変更しない。
- 表示モードを切り替えても、タイマー・ステージ・ミュート状態を維持する。

### 音響

- 現在の `AudioEngine` は `init` / `playAmbient` / `playLoyly` / `setMuted` のみを公開し、`AudioContext` とマスターゲインはフック内部に閉じている。空間音響は追加ではなくインターフェース変更になるため、公開範囲の設計と既存テストへの影響を作業に含める。
- `useAudioEngine` はフックの呼び出しごとに `AudioContext` を作る。3D層で再度呼ばず、contextが保持する単一の `audio` をpropsで受け取る。
- 既存のユーザー操作による初期化と音量制御を維持する。
- ストーブや注水口は位置を持つ音として扱う。風などの環境音は周囲を包む音として設計する。
- カメラの位置と向きをリスナーへ反映する。
- 2Dモードに戻した際の定位・接続を定義し、二重再生や音量の急変を防ぐ。

## 5. 実装フェーズと完了条件

### フェーズ1：素材調査と試験書き出し

**作業**

- シーンの形状、材質、テクスチャ、植栽、モディファイアの負荷を調査する。
- サウナ室と窓外の景色を標準GLBとして試験出力する。圧縮は未適用でよいが、後から差し込める構造にする。
- `blender/` のGit除外と、入力 `.blend` のハッシュ記録・入手手順を整える。
- 材質の欠落、座標、スケール、カメラをブラウザで確認する。
- サウナ着席視点の画像と、サイズ・描画負荷・読み込み時間の初期計測を残す。

**完了条件**

- 木目・主要な形状・ガラスが大きく破綻せず表示できる。
- ブラウザ向けに作り直す材質と、重い要素が特定できている。
- 画質と性能の基準となる比較画像・計測結果がある。
- 書き出し処理を、記録された入力から再実行できる。

### フェーズ2：体験できる最小版

**作業**

- アプリへ3D表示を統合し、サウナ着席・見回し・既存音響を接続する。
- 3D層をフラグで囲み、既定では2D体験が変化しない状態でマージできるようにする。
- ロウリュ通知と蒸気の最小表現を実装する。
- 3D／2D切り替え、読み込み表示、失敗時の2D復帰を実装する。
- リサイズ、UI非表示、タッチ操作、リソース解放を整える。

**完了条件**

- 入室して見回し、音と蒸気を伴うロウリュができる。
- 画質・操作感を実ブラウザで確認できる。
- 切り替えやロード失敗で既存のセッションが壊れない。
- フラグを無効にした状態で、2D体験とバンドルサイズが従来どおりであることを確認できる。

### フェーズ3：施設全体への展開

**作業**

- 水風呂、外気浴、主要な庭を追加する。
- 水面目線とリクライニング目線を設定し、ステージへ接続する。
- 波紋・注水の表現を実装する。
- まずフェードで遷移を完成させ、連続移動を追加する場合は経路を検証する。
- 遷移の開始・完了を単一の状態へ統合し、既存の2系統のタイマーと3D側を整合させる。

**完了条件**

- サウナ → 水風呂 → 外気浴 → サウナの一連の体験が通して動く。
- 各視点で壁や家具に埋まらず、見回しても大きな欠落がない。
- UI・音・視点・タイマーの遷移が整合している。

### フェーズ4：雰囲気の仕上げ

**作業**

- 昼／夕暮れ／自動の照明と環境の補間を実装する。
- `AudioEngine` のインターフェースを拡張し、空間音響を実装する。既存の音響テストを更新する。
- 庭の控えめな動き、呼吸・ブルーム演出を追加する。
- ベイクした陰影と昼夕の照明が矛盾しないか確認する。
- 自動時間帯の進み方と、2周目以降の扱いを定義する。

**完了条件**

- 木・石・布・水の質感と、温かな室内・涼しい外気の雰囲気が伝わる。
- 昼夕の変化と音が自然につながり、演出が操作や視認性を妨げない。
- 2Dモードでも音の定位と音量が従来どおりに戻る。

### フェーズ5：最適化と最終検証

**作業**

- 計測結果に基づき、植栽の間引き・インスタンス化・LOD・材質統合を選ぶ。
- Draco等の形状圧縮と、KTX2等のテクスチャ圧縮を必要に応じて導入する。デコーダは `public/` へ配置し、ベースパス付きで参照する。
- 解像度、影、透明表現、効果の品質を端末に応じて調整する。
- 長時間利用、繰り返し切り替え、通信失敗、WebGLコンテキスト喪失時を確認する。
- 計測結果をもとに、既定モードを2Dのままにするか3Dへ変えるかを判断する。

**完了条件**

- 対象環境ごとの画質と性能が計測され、未検証環境が明示されている。
- 読み込み・描画失敗時も2Dで継続できる。
- モード切り替えを繰り返しても描画ループやリソースが増え続けない。
- 既定モードの判断根拠が計測結果として残っている。

## 6. 性能目標と検証方法

以下は初期目標であり、達成済みの値ではない。フェーズ1で対象端末・ブラウザ・画面サイズ・画質を記録し、必要に応じて調整する。

| 指標 | 初期方針 |
| --- | --- |
| 転送サイズ（モデル） | 施設全体のモデルと必要テクスチャで10〜18MBを仮目標とし、画質との両立を検証する |
| 転送サイズ（JS） | Three.js等は3D用チャンクへ分離する。2D利用時の初期JSを現状から増やさないことを基準とし、3Dチャンクの転送量は別途計測する |
| PC | 60fpsを目標にフレーム時間と瞬間的な落ち込みを計測する |
| モバイル | 低〜中画質で30fps以上を目標に実機で確認する |
| 初期表示 | 2Dで待機できるようにし、ネットワーク条件と3D操作可能までの時間を記録する |
| メモリ | テクスチャ寸法、描画リソース数、切り替え前後の推移を確認する |
| 描画負荷 | ブラウザ実行時のドローコール、三角形数、影・透明描画の負荷を測定する |

GLB容量と描画負荷は別の指標として扱う。Draco圧縮だけではドローコールや表示する三角形数は減らない。JPEG/WebPで転送量を削減しても、GPU上のテクスチャメモリ削減とは限らない。

### コードの検証

- TypeScript：`bunx tsc -b` など、参照先の設定まで含めて確認する。`bun run build` は `vite build` のみで型チェックを行わないため、型エラーはビルドで止まらない。
- 既存テスト：`bun run test`
- 静的検査：`bun run lint`
- 本番ビルド：`bun run build`
- 現在のGitHub Actionsはビルドのみを実行し、型チェック・テスト・静的検査を含まない。3Dでコード量が増える前に、これらをワークフローへ追加する。
- 新しいテストは、ロウリュ通知の重複防止、ロード失敗、モード切り替え、セッション維持など重要な挙動を対象にする。

### ブラウザの検証

- 開発環境に加え、本番ビルドでモデル・デコーダー・テクスチャのURLを確認する。ベースパスは `/sauna-simulator/` に固定されているため、既存の背景画像と同じく `import.meta.env.BASE_URL` を前提に解決する。圧縮を導入する場合、デコーダーのパスをCDN既定値のままにしない。
- 入室、ロウリュ、水風呂、外気浴、再入室、時間帯切り替え、UI非表示、2D／3D切り替えを通して確認する。
- マウスとタッチ、画面リサイズ、バックグラウンド復帰、動きを減らす設定を確認する。
- ロード途中のモード変更、モデルの404、WebGL非対応・コンテキスト喪失時の復帰を確認する。
- デスクトップのウィンドウ縮小のみをモバイル実機検証として扱わない。
- 各ステージの代表画像と計測条件・結果を保存する。静止画での確認と、操作・性能の検証を区別する。

## 7. 主な不確実性と対応

| 不確実性 | 対応 |
| --- | --- |
| 元の材質をGLBへ移すと印象が変わる | サウナ室で早期に比較し、必要なベイクと材質再構築を決める |
| 庭・ガラス・蒸気で負荷が上がる | 効果を個別に計測し、端末別に品質を調整する |
| 昼夕切り替えと固定のベイク照明が矛盾する | ベイク対象を選び、必要なら時間帯別の表現を検討する |
| 既存カメラが体験用の高さや向きに合わない | 体験用視点を新設し、360度の見え方を確認する |
| カメラ移動で壁抜けや不快な揺れが起きる | 初期はフェードとし、移動経路・速度を確認後に追加する |
| 読み込みや切り替えがセッションへ影響する | セッション状態と描画のライフサイクルを分離する |
| 元データがGit管理外のため再現性が下がる | 入力のハッシュと入手手順を記録し、書き出し記録から追跡できるようにする |
| GLBをコミットすると履歴が肥大する | 確定版のみコミットし、容量が問題になれば外部ホスティングへ切り替える |
| 未完成の3D層が自動デプロイで公開される | フラグで囲み、既定を2Dに保ったままマージする |
| 空間音響が既存の音響実装と衝突する | インターフェース変更として扱い、2D復帰時の挙動とテストを同時に整える |
