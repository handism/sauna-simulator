# 庭の木々を別GLBに分け、準備完了の後に読み込む（2026-09-27）

前回の [GLBの圧縮](../glb-filter/README.md) で3D用の取得は11.10MBになったが、30秒の期限内に準備完了するには約3.0 Mbps以上が必要だった。取得量の大半は庭の木々で、建物・水・室内の見え方には関わらない。そこで木々を別のGLBに分け、3Dはそれ以外だけで準備完了にし、木々は後から足すようにした。

## 分け方

`scripts/compress_web_glb.mjs --garden <path>` が、書き出したGLBから `GARDEN` の7ノードを `sauna-garden.glb` へ移す。

| ノード | 圧縮後 |
| --- | ---: |
| `Fine canopy leaves` | 2.83MB |
| `V6 clustered tree leaves`（林のカード） | 1.73MB |
| `Woodland fern` | 0.90MB |
| `V5 overhead canopy bough`（樹皮） | 0.88MB |
| `V11 maple clustered lobed foliage 0〜2`（近景のモミジ3体） | 0.75MB |

- どれも画像を使わず、水の箱（`WATER_BOX`）から離れていて水より上にある。材質は本体と共有しない（林のカードは専用の ` card` 材質）。
- 各ノードのメッシュ・材質・アクセサ・bufferViewだけを取り出して番号を振り直し、それぞれを従来と同じ方式（EXPONENTIALフィルター、全頂点を許容誤差内で検査）で圧縮する。bufferViewごとの圧縮なので、分けても合計はほぼ同じ（9,842,672 → 2,725,640＋7,117,228 bytes）。
- 分割前の配信GLBと比べ、両ファイルを復号した全73ノードの変換・材質・アクセサ（min/max含む）・頂点とインデックスのバイト列、画像6枚がすべて一致した。
- `--garden` を付けなければ同じ入力から分割前の配信GLB（sha256 64eb0d1a…）がバイト一致で再現される。Blenderは再実行していない（入力は前々回の可逆GLBを復号したもの）。
- 最初は近景のモミジを本体に残した（本体3.48MB）が、1.6 Mbpsで準備完了が28.3秒と期限に近かったため庭へ移した。

## ブラウザ側

`SaunaScene.tsx`：

- 本体・シーン定義・プローブで準備完了（`onReady`、期限30秒の解除）にしてから `sauna-garden.glb` を取得する。並行して取ると低速回線で本体の取得が遅れるため、準備完了の後に始める。
- 取得後は本体と同じ材質処理（`prepare`：葉・ノイズ色・林のカード・照度・反射プローブなど）を行い、`hdrOutput.ts` の `compile()` で実際に描くHDRパス用のシェーダーを `compileAsync` で事前にコンパイルしてからシーンに加える。水中の三角形があれば失敗扱いにする（側面の像を作らないため）。
- 影は動かない光源7灯すべて静的なので、追加時に `lighting.refreshShadows()` で一度だけ描き直す（モミジ灯の影も木々から落ちる）。水面の鏡像の状態にも追加の有無を入れて描き直させる。180フレームの計測はリセットする。
- 庭の取得・解析・コンパイルの失敗は3D全体の失敗にしない（`data-garden="failed"`、2Dへ戻らない）。終了・コンテキスト喪失・期限切れの後に届いた庭は捨て、未追加のまま解析済みの庭は終了時に解放する。
- DOM属性：`data-garden`（`loading`／`ready`／`failed`）、`data-garden-ms`（3D開始から庭の追加まで）。材質数の属性は本体と庭の合計。
- `SceneMode` は庭の読み込み中、状態表示を「ドラッグ / スワイプで見回す · 庭の木々を読み込み中」にする。

読み込み中の見え方（昼、標準画質、左が庭なし・右が庭あり）：[サウナ](sauna-without-garden.jpg)／[庭あり](sauna-with-garden.jpg)、[水風呂](water-without-garden.jpg)／[庭あり](water-with-garden.jpg)、[外気浴](totonou-without-garden.jpg)／[庭あり](totonou-with-garden.jpg)。建物・デッキ・石・草地・低い草は揃っていて、林・シダ・頭上の枝・近景のモミジがない。外気浴の遠景は木々がなく草地と空だけになる。

## 帯域制限での読み込み

`bun run test:browser:network` のプロファイルを更新した。1.6 Mbpsは準備完了に変え、期限切れ・手動取り消しは0.8 Mbpsで確認する。準備完了のプロファイルでは、庭の取得が本体GLBの完了後に始まること、読み込み中の状態表示、庭の追加、庭の取得が帯域制限を受けていることも確認する。同じビルドで3回実行し、5件×3回すべて成功（自動再試行なし、ページエラー0件）。全値は [network.json](network.json)。

| プロファイル | 分割前（[前回](../glb-filter/README.md)） | 準備完了 `data-load-ms` | 庭の追加 `data-garden-ms` |
| --- | --- | --- | --- |
| 12 Mbps・80ms | 8.73〜8.78秒 | 3.88秒 | 9.03〜9.13秒 |
| 4 Mbps・150ms | 24.57〜24.63秒 | 10.24〜10.27秒 | 24.96〜25.01秒 |
| 1.6 Mbps・150ms | 期限切れ（30.13〜30.19秒） | **24.50〜24.51秒** | 60.46〜60.49秒 |
| 0.8 Mbps・150ms 期限切れ | — | 30.18〜30.21秒で2D継続（GLB 0.88MB受信で取り消し、庭は未取得） | 再試行後に追加 |
| 0.8 Mbps 手動取り消し | — | 約4.3秒で取り消し（庭は未取得） | 再試行後に追加 |

- 準備完了までの取得は3.98MB（本体GLB 2.73MB、プローブ2件1.06MB、3D専用JS 0.19MB、JSON）。その後に庭7.12MB。合計は11.10MBで変わらない。
- 1.6 Mbpsでは期限まで約5.5秒の余裕。準備完了までの取得は、3D専用JSの後に本体GLB・プローブを並行して取るため、平均で約159KB/s（公称200KB/s）にとどまる。庭は単独で約199KB/s。30秒以内に準備完了する帯域は、1.6 Mbpsの結果から比例で見積もると約1.3〜1.4 Mbps（未実測。前回の約3.0 Mbpsは遅延・解析を除いた転送だけの目安）。
- 庭が届くまでの時間は同じ帯域なら分割前のGLB全体とほぼ同じで、4 Mbps・1.6 Mbpsでは木々のない状態が約15秒・約36秒続く。

## 画像の比較

分割前（HEADのworktree）と分割後で、Cycles同視点（6カメラ×昼夕）と水風呂ステージ視点（4方向×昼夕）を庭の追加後に撮影した。20枚中12枚がバイト一致、残り8枚も平均ΔE76 0.0043以下・8/255を超えて変わった画素0.007%以下で、同じGLBの再撮影と同程度（[image-comparison.json](image-comparison.json)）。描画する形状・材質は分割前と同じ。

## 限界

- ローカルのプレビューとCDPの帯域制限。モバイル実機（庭の復号・シェーダーコンパイルの時間）・CPU制限・本番CDN・キャッシュ有効時の再訪は測っていない。
- 庭の追加時の1フレームの長さ（静的影7灯の再描画と、事前コンパイルで拾えないシェーダー）は測っていない。
- 約1.3〜1.4 Mbps未満（見積もり）では引き続き30秒以内に準備完了しない。残りの大半はプローブ（1.06MB、float16の生データ）と本体の形状。
- 庭の取得に失敗しても再試行はしない（2D切り替え→3Dで再取得）。

## そのほかの検証

- GPU時間（`bun run test:browser:gpu`、HEADのworktreeと交互に6組）：6条件すべてで中央値の比0.986〜1.003、描画数・形状数は同一。
- 継続利用テスト（`test:browser:soak`）は2回とも、標準・高画質の夕暮れで180フレームに15秒以上かかり失敗した（資源数はそれまでの全標本で一致）。HEADでも同じ箇所で失敗し、この機械では前回の成功時より全画質でフレーム間隔が15〜20%長かった。分割による回帰ではないが、5分以上の継続利用は今回成功していない。
- ブラウザ回帰は3回中2回全件成功。1回目は5回の再生成を繰り返すテストで、ある再生成後の180フレームが15秒以内に終わらず失敗した（単独再実行と後の2回は成功）。
