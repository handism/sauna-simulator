# 初回の描画準備を分割する（2026-10-06、検証候補）

[前回](../shader-cost/README.md)の残件「残りの初回停止を、描画を複数フレームに分けて短くできるか」を検証した。製品コード・配信GLBは変更していない。

## 方法

`diagnose_compile_batches.mjs` が現在のソースを一時ディレクトリへ複製してビルドする。読み込み時の最初の本描画の前に、重いプログラム（頂点・断片の合計16万字超）を使う新しい描画状態を1個／3個ずつ許可する。残りの重い描画だけを保留し、次回同じシーンを描いて続ける。主描画・鏡像の本物の描画先・MSAAを使い、鏡像も各回再生成する。

各回の最後にキャンバス1画素の `readPixels()` で先行する描画の完了を待ち、rAFと20msのタイマーでブラウザへ処理を返す。前回確認したように、この環境の `finish()` だけではMetalの準備の完了を待たない。最後に抑止を解除し、影・鏡像・TAAを更新して通常の全体描画へ戻す。これはWebGL呼び出しを抑止する実験であり、製品向けの実装ではない。

- macOS・Apple GPU、Playwright Chrome for Testing／WebKit、headless。
- 標準画質・1200×800・DPR 1.5・動作抑制・昼・固定解像度・全フレーム描画。
- 各ブラウザで通常→1個→3個→3個→1個→通常。全プログラムの断片出力に毎回異なる名前の、初期値0のuniformを足す（出力へ0を加算）。Metalキャッシュを削除せず初回相当のプログラムを作る。製品のシェーダーそのものの初回時間ではない。
- 描画状態のキーはプログラム、描画先の形式・標本数、ブレンド、深度／色書き込み、alpha-to-coverage。29／31などの数はこの検証が許可したキー数で、ドライバーのパイプライン総数の実測ではない。
- WebGL状態の同期問い合わせ・読み戻し・繰り返し描画の費用を含む。FPSや通常利用の読み込み時間と混同しない。
- タイマーの最長間隔はページ初期化から庭準備完了後500msまで（入室前も含む）。分割ステップの最長時間とは別の指標。

## 結果と判断

Chrome for Testing 153.0.8010.12の通常描画は `data-load-ms` 9.81〜9.86秒、タイマーの最長間隔8.58〜8.60秒。1個ずつでは読み込み12.25〜12.30秒、29回の準備の最長1.32〜1.36秒。3個ずつでは読み込み10.81〜10.82秒、11回の準備の最長1.84〜1.88秒。

Playwright WebKit 26.6でも同じ傾向だった。通常は読み込み9.91〜10.14秒・タイマー最長8.70〜8.90秒。1個ずつは読み込み11.54〜12.11秒・準備最長1.37〜1.56秒、3個ずつは読み込み10.58〜11.23秒・準備最長1.90〜2.11秒。WebKitはSafariそのものではない。

**1個ずつの2回目には、準備ステップの外で9.65秒のタイマー間隔も記録された。** 時刻とフェーズを保存していないため、入室前・準備後などのどこで起きたか、原因は特定できない。準備ステップを短く分けられることと、ページ全体の停止がなくなることは分けて判断する。

最初の準備ステップには軽いプログラムや影など、今回分割しない処理も入る。そのため1個ずつでも1秒以上の待ちが残る。読み戻しと再描画で合計時間も延びる。**製品への採用は保留**とする。

両ブラウザの3ステージの既定視点は各6回、合計36枚が、各ブラウザの最初の通常描画とRGB全画素一致。撮影時だけDOMのUIを非表示にして比較した（初期試行ではcanvasのスクリーンショットにもUIが重なり、タイマーの文字が差になったため、最終撮影から除外）。全周・見回し・夕暮れ／夜の画質確認ではない。

詳細は [Chrome](cft.json)、[WebKit](webkit.json)、[集計](summary.json)。

## 初回調査時点の次の作業

- タイマーとrAFの間隔に時刻・入室／準備／準備完了／庭のフェーズを記録し、ステップ外の停止を切り分ける。
- 重い材質以外の最初の準備を調べる。読み戻しを非同期のフェンスへ置き換えられるかも別に検証する。

## 時刻・フェーズ付きの追試（2026-10-06）

前回のステップ外の9.65秒を調べるため、診断にページ初期化・入室クリック・本体取得／解析／材質準備／リンク待ち・分割準備・本体準備完了・庭取得／解析／リンク待ち／追加・庭の最初の描画の時刻を追加した。10msタイマーとrAFの100ms超の間隔には開始・終了時刻を付け、集計ではその間に重なるフェーズと準備ステップを列挙する。コールバックが返った時点のフェーズだけでは、どこで止まったかを誤るため。庭の `ready` は最初の描画より前なので、その描画も別に記録する。

準備ステップは描画と最後の1画素の読み戻しを分けて計時し、100ms超のWebGL呼び出し（シェーダー情報、状態問い合わせ、描画、読み戻し等）も記録する。描画のフックの中で状態を問い合わせるため、内外の呼び出し時間は重なる。合計してGPU時間やコンパイル時間にしてはいけない。問い合わせの待ちは、それ以前の描画の完了を待つこともあり、その関数自身の処理費用とは限らない。撮影前にタイマーとrAFを止め、撮影・次ステージの停止が読み込み窓へ混ざるのを防ぐ。

追試の条件は前回と同じ（各ブラウザで通常→1個→3個→3個→1個→通常、毎回新しいゼロuniform、キャッシュ削除なし）。計測には同期問い合わせと再描画の費用が含まれ、製品そのものの初回時間や通常のFPSではない。

追試の生データは [Chrome](timeline-cft.json)、[WebKit](timeline-webkit.json)、[時刻付き集計](timeline-summary.json)。前回の `cft.json`／`webkit.json`／`summary.json` は旧版の記録として保持する。スクリプトが変わったため、旧記録を現行スクリプトで集計し直すと拒否される。旧記録の再集計には当時の版が必要。

## プログラム・先行描画の対応付け（2026-10-06）

時刻付き追試の残件「最初の準備のプログラムと先行描画の対応」を確認した。schema 3の診断は、プログラム名・定義・ソース長、分割中に実際に発行した描画の順序、各問い合わせの対象プログラムと直前8回の実描画を記録する。抑止した描画は履歴に入れず、対応付けのための追加のGL状態問い合わせは行わない。100ms未満も含む全 `getProgramInfoLog` を記録し、最初のステップで実描画したプログラムと問い合わせたプログラムを比較する。通常→1個→3個→3個→1個→通常、各ブラウザ6件の同条件で再実行した。

問い合わせの時間はCPUでその呼び出しを待った時間であり、その対象プログラム自身のコンパイル費用とは限らない。直前の描画との順序は確認できるが、その描画が待ちの原因か、キュー内の別の描画・リンク等を待ったかは、このログだけでは確定しない。通常と分割条件は新しいuniformを使う診断であり、記録処理・状態問い合わせ・読み戻しの費用も含む。製品の初回時間やGPU時間として扱わない。

## リンク情報の先行取得・全プログラムの分割（2026-10-06）

前回の次作業「材質の初回情報取得を本描画の前に分ける候補」と「影マスク・短い出力プログラムの初回準備」を、schema 4の診断で別条件として比べた。製品コード・配信物は変更していない。

- `p`（先行取得）：`compile()` の後、最初の描画の前に `renderer.info.programs` の各プログラムを1フレームに1個ずつ、`isReady()`（`COMPLETION_STATUS_KHR`）をrAFで非同期に待ってから `getUniforms()`（three.jsの `onFirstUse`。リンク情報・uniform・attributeの取得）を呼ぶ。`p0` はその後に通常の全体描画、`p1` は従来の重い描画状態の1個ずつの分割へ進む。

- 各ブラウザで通常→p0→1→p1→a1→a1→p1→1→p0→通常（各条件2回）。その他の条件（毎回新しいゼロuniform、キャッシュ削除なし、標準・DPR1.5）は前回までと同じ。

  - キャッシュがある2回目以降の読み込みの延び（46回のrAF＋20ms、約1.4秒）。必要なら2回目以降を短くする方法（1フレームに複数グループ、待ちの短いステップは続けて描く等）。
  - 30秒の期限、温め中の画質・ステージ・時間帯の変更、キャンセル・コンテキスト喪失、影／鏡像の復旧。
  - 他の視点（水風呂・外気浴から入室する場合）での網羅。今回はサウナの視点で温め、ステージ変更で新しい重い状態は出なかった。
  - Safari・Windows・モバイル・遅い端末。

## キャッシュがある2回目の読み込みと時間予算（2026-10-06）

前回の次作業「キャッシュがある2回目以降の延び（46回のrAF＋20ms）の計測と短縮」。schema 7で次を加えた。製品コード・配信物は変更していない。

- `SUI_WARM=1` は各条件を同じブラウザで2回読み込む。1回目は新しいuniformによる初回、2回目は同じuniform（同じシェーダー）で、Metalのキャッシュがある状態。2回目は同じブラウザのプロセス内なので、ブラウザを開き直した再訪問とは異なる（[以前の再訪問](../other-browsers/README.md)の通常の2回目は0.35〜0.6秒）。
- 条件 `v<N>b<ms>`（例 `v1b50`）は、直前にブラウザへ処理を返してからのステップの時間が `<ms>` 以上になったときだけrAF＋20msで返す。初回はほぼ毎ステップが予算を超えるので従来どおり返し、キャッシュがあって短いステップは続けて描く。各ステップの読み戻しによる完了待ちは従来どおり。
- 各ブラウザで通常→v1→v1b50→v1b50→v1→通常の順（それぞれ初回・2回目）。そのほかの条件（キャッシュ削除なし、標準・1200×800・DPR1.5・昼）は前回と同じ。

```sh
SUI_WARM=1 node scripts/diagnose_compile_batches.mjs docs/3d-qa/compile-batches/warm-cft.json.local cft 0,v1,v1b50 2
SUI_WARM=1 node scripts/diagnose_compile_batches.mjs docs/3d-qa/compile-batches/warm-webkit.json.local webkit 0,v1,v1b50 2
python3 scripts/summarize_compile_batches.py docs/3d-qa/compile-batches/warm-cft.json.local docs/3d-qa/compile-batches/warm-webkit.json.local --out docs/3d-qa/compile-batches/warm-summary.json
```

集計は、初回と2回目が同じuniformを共有し、それ以外では共有しないこと、予算なしでは全ステップで処理を返すことも検査する。[集計](warm-summary.json)。

### 判断と次の作業

- 製品化するなら時間予算付き（50ms）にする。初回の停止は約0.4〜0.45秒のまま、キャッシュがあるときの延びは約0.3秒。予算の値の調整（短いほど処理を返す回数が増える）は製品の計測で確かめる。
- 残る2回目の延び約0.3秒は、各ステップの読み戻し（46回）と、隠した材質を除いた本体の描画を鏡像・主描画で余分に1回ずつ行う分。これ以上は、キャッシュの有無をJSから知る方法がないため、待たない描画に分けて費用を比べる必要がある。優先度は低い。
- 次は製品化の設計：部分画像を見せない、30秒の期限、温め中の画質・ステージ・時間帯の変更、キャンセル・コンテキスト喪失、影／鏡像の復旧、水風呂・外気浴から入室する場合の網羅。

## 内部ターゲットでの温めと開始ステージ（2026-10-06）

schema 8の `ov1b50` は、一時ビルドのHDR出力に温め専用のパスを加える。主描画は通常と同じ半浮動小数・MSAA 4のターゲットへ描くが、TAAと最後の画面出力を行わない。鏡像は従来の内部ターゲットへ描く。完了待ちはHDRターゲットの1画素を読み戻す。本体のhostは完全描画まで非表示にし、庭は通常ループを止めてから材質を分割し、画面へ描くGL呼び出しがないことも記録する。製品コード・配信物は変更しない。

`SUI_ENTRY=sauna|water|totonou` は2Dで入室し、指定ステージへ移動してから「3Dを試す」を押す。計測窓は3Dの選択直前にリセットする。撮影は入口から3ステージを一巡し、各入口で通常→候補→候補→通常の順に比較する。

`SUI_HOLD=1` は庭を加える直前、温めの各ステップで処理を返した後、材質を復元した後に、表示canvasをスクリーンショットで撮る。各撮影前に2回のrAFと100msを待つ。DOM操作パネルは撮影用styleで隠す（固定の操作案内 `scene-status` は写る）。**これらの待ち・撮影はロード時間とタイマー間隔に含まれるため、今回は性能比較に使わない。** 集計の `timingComparisonValid` もfalseにする。画面の保持は最初の撮影とのRGB画素差で確認し、`deferredHeavyStates` は温め外で初めて使った重い状態を、ブレンド無効時の係数差を除いて列挙する。

```sh
# engine=cft/webkit、entry=sauna/water/totonouで順番に実行（4194番ポート）。
SUI_HOLD=1 SUI_ENTRY=water node scripts/diagnose_compile_batches.mjs docs/3d-qa/compile-batches/presentation-cft-water.json.local cft 0,ov1b50 2
python3 scripts/summarize_compile_batches.py docs/3d-qa/compile-batches/presentation-*.json.local --out docs/3d-qa/compile-batches/presentation-summary.json
```

集計はschema・現在の診断／製品ソース／一時ビルド／配信物／PNGのハッシュ、入口・条件順序・全準備の完了、処理を返した各ステップの撮影、画面への途中描画がないことを照合する。旧schemaの記録は旧版の記録として保持し、現行集計では拒否する。
