# 画質切り替え時の停止の切り分け（2026-10-03）

製品コード・配信モデルは変更していない。対象は `e9942c7`（描画実装は前回と同じ）。
継続利用の7周目・軽量・夕・サウナで過去2回記録された約417msの停止を調べた。

## 再実行

```sh
SOAK_TIMING=1 bun run test:browser:soak --reporter=json > /tmp/sauna-soak-timing.json
bun run test:browser:gpu e2e/quality-stall.gpu.ts --reporter=json > /tmp/sauna-quality-stall.json
```

`e2e/soak-timing.ts` をページ起動前に入れ、WebGL描画を行うrAFコールバックだけについて、
100msを超えるフレーム間隔・処理時間と前後の状態を記録する。さらにLong Tasksと、
シェーダーのコンパイル・リンク・状態／ログ／uniform取得等の同期WebGL呼び出しを測る。
20msを超える個別の呼び出しと、長い描画コールバック内の呼び出し回数・合計時間を保存する。
`soak-timing` 添付は最大2000イベント（今回の記録は上限未満）。時刻はページの `performance.now()` 基準。
各描画の状態コピーと呼び出しのラップには負荷がある。通常の継続利用テストでは無効。

短い専用診断は、庭の準備後に夕暮れを選び、高画質→軽量→高画質→軽量を各4秒観察する。
GPU診断用configを使うが、GPUタイマーの計測ではなくメインスレッドの経過時間である。
専用診断は動作抑制あり、継続利用は通常の動作設定。どちらもChrome・1280×800・DPR1。

## 観測

- 最初の診断付き継続利用は成功（8周回・40標本）。7周目の標本に最大433.3msが残り、
  その直前の描画コールバックは417.1ms、Long Taskは417ms。タブは非表示になっていない。
- この停止の前後で画質が高画質から軽量に変わっている。他の画質変更でも394〜580msの長い描画がある。
  3Dを作り直す間の無描画期間はフレーム間隔にも現れるため、これを継続描画中の停止と混同しない。
- 追加した短い診断では、最初の軽量への切り替えで描画469.8ms。
  29プログラムの `getProgramInfoLog` が合計407.2ms、58シェーダーの `getShaderInfoLog` が15.0ms。
  同コールバック内で58回のコンパイル・29回のリンクが発行されている。
  2回目の高画質→軽量では100msを超える描画は記録されなかった。

## 解釈と対応範囲

Three.jsの `WebGLProgram.onFirstUse()` はプログラムを初めて使う際にログを同期取得する。
画質の変更は `lighting.setDuskLights()` で光源数を変え、シェーダーの別の組み合わせを必要とする。
観測された待機はこの最初の利用に対応する。ドライバー内部でコンパイル・リンクのどの工程が
何msかかったかまでは測っていない。ログ自体の文字列処理が400msという意味ではない。

7周目だけの経年劣化やTAAの継続利用が原因とは扱わない。既存の180フレーム窓はステージ・画質変更で
消去されるので、切り替え途中で起きた停止が、資源比較のための最終標本に残る場合と残らない場合がある。
資源数のテストが成功しても、切り替えが常に滑らかであることは示さない。

対策候補は画質の切り替えに必要なシェーダーを非同期に準備すること。ただし、準備中の描画、
連続した画質変更、破棄・2D復帰、初回ロード費用の扱いを設計して検証する必要がある。
ログの検査を無効にするだけでは他の同期取得へ待機を移す可能性があり、対策とはしていない。
今回の作業は原因調査と再現手順まで。実機・GPU総メモリ・音声ノード数は対象外。

`values.json` にPlaywrightの成功状態・再試行回数・添付そのものを保存した。
最初の継続利用は5種類のWebGL呼び出しだけを監視し、短い診断以降でログと合計時間を追加した。

## 対策：新しい画質のプログラムを旧画質のまま準備する（同日）

描画中のシーンで画質を変えると、`lighting.withQuality()` で一時的に新しい画質の光源・影の数にして
`hdrOutput.ts` の `compile()`（HDRターゲットで `compileAsync`）だけを行い、旧画質のまま描き続ける。
プログラムのリンクが終わってから画質を適用する（`data-quality` は適用した画質。連続した変更は最後の選択だけ、
破棄後は適用しない）。影マスクを使うかどうかも適用した画質に従う。

実装中に見つかったthreeの挙動が2つあり、どちらも対処した。

- `compileAsync` は各材質の「現在のプログラム」の準備を待つ。間に旧画質で描くと、光源に依存する材質は
  旧画質のプログラムへ戻るため、待つ対象が準備済みの旧プログラムになり、新プログラムの完了前に解決していた
  （最初の試作では適用時に29プログラムの初回使用が残った）。`compile()` は、コンパイル直後に取得した
  プログラムそのものの `isReady()`（`KHR_parallel_shader_compile`）も待つ。
- 光源に依存しない材質（記録では空・ガラス2つと `SHADER_NAME` が空のプログラム5つ）は描画時に影の有無を比べないため、旧画質の描画でも
  コンパイルした新しいプログラムを使い続け、その初回使用で約90〜145ms止まった。コンパイル後に
  `needsUpdate` を付け、次の描画で照明に合うプログラムを選び直させる（キャッシュ済みなので再コンパイルはない）。

診断 `soak-timing.ts` に、各プログラムの `SHADER_NAME`・作成順・作成時刻と、長い描画の中で初めて使われた
プログラムの一覧を加えた（この切り分けに使った）。

### 結果

`e2e/quality-stall.gpu.ts`（高画質→軽量→高画質→軽量、各4秒）を、変更前（`848d5eb` のworktree、
同じ診断）と交互に3回ずつ。全6回成功・再試行なし。

| | 最初の高画質→軽量 | 100msを超える描画 | 切り替え後のLong Task |
|---|---|---|---|
| 変更前 | 533・466・477ms（29プログラムの初回使用） | 各1回 | 466〜533ms |
| 変更後 | 100ms以下 | 0回 | 75〜84ms（適用時の1回） |

変更後も、選択時の同期部分（29プログラムの作成とコンパイル・リンクの発行、50ms前後）と、
適用時の初回使用（ログ取得等で数十ms）が残る。軽量→高画質・2回目以降の切り替えでは100msを超える描画はない。
変更後の継続利用（`SOAK_TIMING=1`）は成功（322.3秒・8周回・40標本、再試行なし）。100msを超える描画は0回で、
40標本の最大フレーム間隔はすべて50ms以下（変更前は7周目に416.6〜433.3ms）。100msを超えるLong Taskは10回あり、
すべて3Dの初回ロード・再生成の直後（`data-garden=loading`、535〜826ms）で、ロード時のコンパイル費用（対象外）に当たる。
値は `async-compile.json`（各回のPlaywrightの状態と `soak-timing` 添付）。

範囲：Chrome（ANGLE Metal）・1280×800・DPR1、メインスレッドの経過時間のみ。`KHR_parallel_shader_compile` の
ない環境では `isReady()` が常に真で、従来どおり初回使用で待つ（準備中の描画が増えるだけで悪化はしない）。
実機・他のブラウザは未確認。初回ロード時のコンパイル費用は対象外。
