# 3Dの初回ロード時のコンパイル（2026-10-04）

画質切り替えの停止の対策（`e6bb054`、[quality-stall](../quality-stall/README.md)）の残件「初回ロード時のコンパイル費用」。
継続利用で3Dの初回ロード・再生成の直後に535〜826msのLong Taskが10回残っていた。

## 再実行

```sh
bun run test:browser:gpu e2e/load-compile.gpu.ts --reporter=json > /tmp/sauna-load-compile.json
SOAK_TIMING=1 bun run test:browser:soak --reporter=json > /tmp/sauna-soak-timing.json
```

`load-compile.gpu.ts` は入室→庭の準備完了＋3秒→2Dへ切り替え→3Dを試す→庭の準備完了＋3秒を通し、
`soak-timing.ts` の記録（Long Tasks、描画ループの外の1ms以上の同期WebGL呼び出し `outside`）を添付する。
読み込み時の最初の描画は描画ループ（rAF）の外で行われるため、既存の記録では見えなかった。
Chrome（Playwright・headless）・ANGLE Metal・macOS・1280×800・DPR1・動作抑制あり（GPU診断用config）。
メインスレッドの経過時間で、GPU時間ではない。

## 観測（変更前）

- 初回ロードの長いタスクは約0.78秒。うち41プログラムの初回使用（`getProgramInfoLog`）が約0.54秒。
  プログラムは作成と同時に初めて使われ（作成時刻＝使用時刻）、並列コンパイルが全く効いていなかった。
  `SaunaScene` は最初の `draw()` で全材質のプログラムを作り、threeの `onFirstUse()` が1つずつドライバーを待つ。
- 同名の材質が4〜6プログラムになっていたのは、パスの違い（鏡像・影マスク・主パス）ではなく、
  シーン内の別材質（側面の像の複製 `SUI_SIDE_IMAGE`・`SUI_SIDE_FLIPPED`・`SUI_SIDE_TESTED`、`SUI_HARD_SHADOW` の奥の壁、
  影マスクの `SUI_SHADOW_MASK`）だった（定義を一時的に記録して比較。記録処理は外した）。
  どれもシーン全体の `compile()` で作れる。

## 対策

最初の描画の前に、`hdrOutput.ts` の `compile()`（HDRターゲットで `compileAsync`、作ったプログラム自体の `isReady()` も待つ）で
シーン全体を準備する。待つ間に画質が変われば（準備完了前の画質変更は即時適用）準備し直す。
待つ間に退出・失敗すれば描かない。

### 別のページが描いている間は完了しない

最初の版で通常のブラウザ回帰を通すと `temporal-aa.e2e.ts` が4回中4回、2つ目のページの準備完了を30秒待って失敗した。
止まっていたのではなく、何も描いていないコンテキストの `COMPLETION_STATUS_KHR` が、
同じブラウザで別のページがWebGLを描き続けている間なかなか真にならなかった
（2つ目のページの全32プログラムが約7秒未完了、`data-load-ms` 7706ms）。
1ページ目を閉じてから開くと556ms、描画中のページがあると4555ms〜30秒超。前のテストで閉じ忘れたページが残ると1ページ目でも起きた。

| ポーリング中に足した処理（別ページ描画中） | `data-load-ms` |
| --- | --- |
| `gl.flush()` | 30秒超（2回とも準備完了せず） |
| 1×1の画面外ターゲットのクリア | 4228・6614・23679ms |
| 表示中のcanvasのクリア | 994・1682・1716ms |

canvasを更新すると進むが、描画中の画質変更では表示中のフレームを消してしまい、原因も特定できていないため採らなかった。
代わりに読み込み時の待ちを1秒まで（`compile()` の `within`）とし、残りのプログラムは従来どおり最初の描画で同期で待つ。
通常は約0.3秒で完了するので上限には届かない。画質の変更・庭の追加は描画ループが動いている間に待つため上限を設けていない
（観測した範囲では描画中のページは遅れなかった。庭は1回目の版でも7706→7887msと約0.2秒で準備された）。

同じ条件（1ページ目が描画中、2つ目のページを `?temporal=off`・DPR 1.5・動作抑制で開く）で各3回：

| 版 | 別ページ描画中 | 単独 |
| --- | --- | --- |
| 変更前 | 2214・2825・4666ms | 753ms |
| 変更後（上限1秒） | 1693・1796・1689ms | 546ms |

変更前の同期の初回使用もこの条件では遅くなり、上限付きの変更後のほうが短い。

## 結果

変更前（`e6bb054` のworktree、同じ診断）と交互に3回ずつ。全6回成功・再試行なし。値は `values.json`。

| | 初回ロードの最長タスク | `data-load-ms` | 再生成の最長タスク | 再生成の `data-load-ms` |
| --- | --- | --- | --- | --- |
| 変更前 | 776〜783ms（41プログラムの初回使用 542〜545ms） | 831〜838ms | 624〜627ms（40〜41、446〜450ms） | 662〜667ms |
| 変更後 | 165〜167ms（プログラムの作成）＋103〜108ms（最初の描画、10プログラム・37〜40ms） | 433〜444ms | 117〜121ms＋86〜89ms | 506〜511ms |

庭の準備完了（`data-garden-ms`）も931〜965ms→533〜547ms。変更後に残る長いタスクは、
29〜41プログラムの作成とコンパイル・リンクの発行（同期）と、最初の描画で作られる影の深度材質など（各数ms）。

継続利用（`SOAK_TIMING=1`、変更後）：**320.0秒・8周回・40標本で成功**（再試行なし）。形状128、テクスチャ軽量17／標準・高画質34で
従来と同じ。100msを超える描画0回、全標本の最大フレーム間隔16.8ms。100msを超えるLong Taskは11回（108〜194ms）：
アプリ起動1回（194ms、3D以前）と、3Dの初回ロード・再生成ごとのプログラム作成または最初の描画（108〜167ms）。
変更前は3Dのロード・再生成の直後に535〜826msが10回。値は `soak.json`。

範囲：Chrome（ANGLE Metal）・DPR1のみ。`KHR_parallel_shader_compile` のない環境では `isReady()` が常に真で、
従来どおり最初の描画で待つ。実機・他のブラウザ、別ページが描画中のときに完了しない原因は未確認。

## 原因：トレースの画面転送（2026-10-05、確認）

上の「別のページが描いている間は完了しない」の原因を切り分けた。**別のページの描画そのものではなく、そのページをDevToolsが画面転送していること（Playwrightのトレースの `screenshots`）が条件だった。**
通常のブラウザ回帰は `trace: retain-on-failure` で全テストのトレースを記録するため、`temporal-aa.e2e.ts` の2つ目のページで起きていた。利用者の環境では、DevToolsで別のタブを画面転送しない限り起きない見込み。製品の動作は変えていない（コメントと記録のみ更新）。

- 読み込み時の上限1秒を外したビルド（`840b5c1` のworktreeで `SaunaScene.tsx` の `within` を除く）で `temporal-aa.e2e.ts` を流すと、トレースありは3回とも2つ目のページの庭の準備が30秒で間に合わず失敗し、`--trace off` では成功した（14.9秒）。
- `scripts/diagnose_parallel_compile.mjs` で、ページA（別のbrowser context）の条件を変えてページBの3Dを読み込んだ（Chrome 154.0.8037.97／macOS、1200×800・DPR 1.5、2回）。時間は最初の `linkProgram` からの経過。

| ページA | Aのトレース | 最初の完了 | 中央値 | 全50プログラム | `data-load-ms` |
| --- | --- | ---: | ---: | ---: | ---: |
| なし | — | 48〜49ms | 134〜161ms | 389〜467ms | 434〜503 |
| 3D（描画中） | — | 49ms | 304〜316ms | 875〜879ms | 793〜828 |
| 重いWebGL（描画中） | — | 48〜49ms | 248〜279ms | 989〜1082ms | 915〜956 |
| 3D | DOMスナップショット | 49〜50ms | 303〜304ms | 821〜897ms | 800〜836 |
| 3D | 画面転送 | **18.6秒** | 19.1秒 | 26.2〜26.4秒 | 26040〜26252 |
| 重いWebGL | 画面転送 | 48〜49ms | 1961〜2067ms | 6.0〜6.4秒 | 5798〜6195 |

- 画面転送がなければ、別のページが描いている間も完了は止まらずに進み、全体が約2倍遅くなるだけ（0.4〜0.5秒→0.8〜1.1秒）。上限1秒はこの範囲をほぼ覆う。
- 画面転送中は、3Dのページが相手だと最初のプログラムまで約19秒、どれも完了しない。ページBが描き始めるとすぐ進む（上限1秒の製品ビルドでは最初の完了1.35秒・`data-load-ms` 6.6秒、[製品ビルドの値](parallel-compile-product.json)）。以前の「表示中のcanvasのクリアで進む」と同じ傾向。
- 小さなプログラム40個の対照は、画面転送中でも0.24〜0.65秒で完了した（単独0.24秒）。重いシェーダの非同期コンパイルだけが待たされる。
- 画面転送がGPUプロセスの中でどの順番で処理を止めるか（スケジューラーの優先度など）は、Chromeの内部の問題で調べていない。

範囲：Chrome（ANGLE Metal）・macOSのみ。他のブラウザ・実機、DevTools以外の画面共有・録画（OSの画面収録など）でも起きるかは確かめていない。[値](parallel-compile.json)。

bun run build && bun run preview -- --host 127.0.0.1 --port 4191 --strictPort &
node scripts/diagnose_parallel_compile.mjs http://127.0.0.1:4191/sauna-simulator/ docs/3d-qa/load-compile/parallel-compile.json 2
