# 3D読み込みの帯域制限検証（2026-09-27）

`e2e/scene-loading.network.ts`（`bun run test:browser:network`）で、2D入室後に「3Dを試す」を押してからの取得を、CDPの帯域・遅延制限下で測った。全測定値は [results.json](results.json)（3回分の添付JSON）。

## 条件

- Chrome 154.0.8037.57、macOS headless、1280×800、DPR1、ローカルの `vite preview`（127.0.0.1:4175）。
- 2Dの画面は制限なしで読み込み済み。制限は「3Dを試す」の直前から `Network.emulateNetworkConditionsByRule` で掛け、キャッシュとService Workerは無効。
- 3つの実験用プロファイル（実在の回線種別の名前ではない）：
  - 12 Mbps・遅延80ms：読み込み中に水風呂へ進み、そのまま準備完了まで待つ。
  - 1.6 Mbps・遅延150ms：30秒の期限切れで2Dへ戻ることを確認し、制限解除後に外気浴で再試行。
  - 1.6 Mbps・遅延150ms：GLBの応答を受信し始めてから「2Dに切り替え」で手動取り消し、制限解除後に再試行。

## 取得量（圧縮後の転送量）

| ファイル | バイト |
| --- | ---: |
| `SaunaScene-*.js`（3D専用チャンク） | 187,358 |
| `sauna.glb` | 16,369,477 |
| `irradiance.bin` / `reflection.bin` | 各531,212 |
| JSON 3件 | 計2,915 |
| 合計 | 17,622,174 |

GLBが93%を占める。30秒の期限内に取得を終えるには、遅延・解析を無視しても約4.7 Mbps以上が必要（1.6 Mbpsでは約88秒）。

## 結果（3回とも3件成功、自動再試行なし、ページエラー0件）

| プロファイル | 結果 | 3回の値 |
| --- | --- | --- |
| 12 Mbps | 準備完了（`data-stage=water`） | `data-load-ms` 13,112 / 13,100 / 13,102ms。GLB取得12.35〜12.36秒 |
| 1.6 Mbps 期限切れ | 30秒で2D継続、GLBは取り消し | 押下から30,192 / 30,205 / 30,185ms。GLBは3.71MB（22.7%）受信時点で `net::ERR_ABORTED` |
| 1.6 Mbps 手動取り消し | 2D切り替えでGLBを取り消し | 押下から約3.3秒。GLB 0.13MB、`.bin` 2件も取り消し |

- 期限切れでは2つの `.bin` は約10.2秒で取得済みだったため取り消し対象はGLBのみ。手動取り消しでは未完了の3件がすべて取り消された。
- いずれも取り消し後に3D用のcanvasは残らず、2Dの操作（外気浴への遷移）を継続でき、ミュート状態も保持された。
- 制限解除後の再試行はGLBを最初から取り直し（キャッシュ無効のため）、約0.5秒で外気浴の3Dが準備完了した。

## 判断

- 30秒の期限・取り消し・2D継続・再試行は低速回線でも設計どおりに動く。
- 一方、4.7 Mbps未満では3Dが期限内に完了しない。現状は読み込み中の案内と期限切れ後の2D継続で扱っており、GLBの分割・段階的読み込みや容量の削減は未着手。
- 追記（同日）：GLBを許容誤差つきのフィルターで9.84MBに縮め、目安は約3.0 Mbpsになった（[記録](../glb-filter/README.md)）。

## 限界

ローカルのプレビューとCDPの帯域・遅延制限であり、CPU制限・モバイル実機・パケット損失・本番CDN・HTTPキャッシュ有効時の再訪は測っていない。
