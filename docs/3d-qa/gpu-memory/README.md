# 3DのGPUメモリ（2026-10-04）

継続利用・音声ノードの検証で残っていた「GPU総メモリ」。

## 再実行

```sh
bun run build && bunx playwright test e2e/gpu-memory.e2e.ts --reporter=json > /tmp/sauna-gpu-memory.json
```

`gpu-memory.ts` が検証ブラウザ内でWebGL2の確保・解放の呼び出し（`texImage2D/3D`・`texStorage2D/3D`・`compressedTexImage2D`・`copyTexImage2D`・`generateMipmap`・`bufferData`・`renderbufferStorage(Multisample)` と `delete*`）をGLオブジェクトごとに数え、
コンテキストごとのテクスチャ・バッファ・レンダーバッファのバイト数と描画バッファの推定値を返す。
データが必要とするバイト数（RGBは1テクセル4バイト）で、ドライバーの詰め物・整列・内部コピー・プログラムは含まない。ドライバーの報告値ではない。
Chrome（Playwright・headless）・ANGLE Metal・macOS・1280×800・DPR1・`?resolution=fixed`（動的解像度は描画先の大きさを変えるため止める）。

テストは3画質で全ステージとロウリュを一度通して初回の確保を済ませた後、軽量→高精細→標準でステージを一巡する周回を2回、2D→3Dの再生成3回の後にも同じ周回を行い、
同じステージ・画質の合計がすべて一致すること、2Dへ戻した旧コンテキストが失われ（＝すぐ解放され）バッファ・レンダーバッファを残していないことを確かめる。
ロウリュを初めて押すと蒸気のテクスチャ・バッファ（約22KB）を確保するため、暖機で押しておかないと軽量の値が周回で揃わない（不具合ではない）。

## 観測（変更前、`a3d7ad5`）

- 周回・再生成をまたいで増え続けるものはなかった。合計（MiB）は軽量160.9・標準247.2〜247.5・高精細459.5〜460.8。
- 高精細のテクスチャ293MiBの大半は影を描く7灯の影マップで、2048²の深度（16MiB）と並んで **RGBA8の色テクスチャ（16MiB）** を持っていた。
  three 0.186の影マップは色付きのレンダーターゲット＋深度テクスチャで、シェーダが読むのは深度テクスチャだけ（`WebGLLights.js`、VSM以外）。色は書かれるだけで読まれない。標準（1024²）では1灯4MiB。
- 描画バッファは `antialias: true`（4倍MSAA＋深度）で約35MiB。HDR出力の端末ではシーンを4倍MSAAの半精度ターゲットに描き、canvasには全画面三角形を1枚出すだけなので、canvasのMSAA・深度は使われていない。
- 2Dへ戻した旧コンテキストは失われず、three内部の小さなテクスチャ5つ（1×1・16×16、1,060バイト）と描画バッファがGCまで残っていた（`renderer.dispose()` はコンテキストを失わせない）。

## 対策

- `lighting.ts` の `narrowShadowColor()`：影マップのレンダーターゲットが `shadow.map` に代入された時点（確保の前）で色テクスチャを `RedFormat`（R8）にする。
  threeは最初の影の描画で影の種類の変更として必ずターゲットを作り直すため、事前に作って渡すことはできない。
- `hdrOutput.ts` の `createRenderer()`：先にWebGL2コンテキストを `antialias: false, depth: false` で作り、`EXT_color_buffer_float` があればそれでレンダラーを作る。なければそのコンテキストを失わせ、従来どおり `antialias: true` で作る（シーンをcanvasへ直接描くため）。
- `SaunaScene` の後始末で `renderer.dispose()` の後に `renderer.forceContextLoss()`。

## 結果（変更後）

| 画質 | 変更前 | 変更後 | 主な差 |
|---|---|---|---|
| 軽量 | 160.9 | 129.7（−19%） | 描画バッファ 35.2→3.9 |
| 標準 | 247.2〜247.5 | 195.0〜195.3（−21%） | ＋影の色 7×4→7×1 |
| 高精細 | 459.5〜460.8 | 344.2〜345.6（−25%） | ＋影の色 7×16→7×4 |

単位はMiB（1280×800・DPR1）。描画バッファの差は画素数に比例するので、DPR 1.5・2の画面ではその2.25・4倍になる。
旧コンテキストは2Dへ戻した時点で失われる。

画像は変わらない：3ステージ×昼夕夜×3画質の27枚（PNG、動作抑制・UI非表示）を変更前・変更後で交互に2回ずつ撮り、すべて全画素一致した（比較用の一時テストはコミットしていない）。
影マップは画質の変更時だけ描くため、R8化は毎フレームの費用にはほぼ関係しない。canvasのMSAAをやめた分のGPU時間は[後で測った](../canvas-msaa/README.md)（標準・DPR 1.5で1〜2%減）。

## 範囲外

- ドライバー・ブラウザが実際に確保する量（詰め物・圧縮・合成用のコピー）、プログラム、実機（DPR 2〜3）。
- 残りの大きいもの：4倍MSAAの半精度の描画先（1280×800で31MiB＋深度16MiB）、高精細の鏡像の4倍MSAA（31MiB）、標準・高精細の鏡像・TAAの履歴、1024²・ミップ付きのテクスチャ6枚（32MiB、GLBの画像とみられる。由来は確かめていない）、頂点バッファ28MiB。
