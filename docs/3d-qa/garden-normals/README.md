# 庭GLBの法線を8bitに（2026-10-04、採用）

[GPUメモリ](../gpu-memory/README.md)の残件「頂点バッファ28MiB」。

## 内訳

配信中のGLBの頂点データ（復号後、GPUへ送る量）は合計27MiBで、3/4が庭（`sauna-garden.glb`、約71万頂点）：

| | POSITION | NORMAL | インデックス | UV | 色 | 計 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 庭 | 8.11 | 8.11 | 3.44 | 1.17 | – | 20.8 |
| 本体 | 1.76 | 1.76 | 0.61 | 1.60 | 0.49 | 6.2 |

単位MiB。すべてfloat32（[glb-filter](../glb-filter/README.md) のEXPONENTIALフィルターは転送量を減らすが、復号後はfloat32のまま）。

## 変更

`scripts/compress_web_glb.mjs` が庭GLBの法線だけを8bitのoctフィルター（meshopt `OCTAHEDRAL`、出力は正規化int8・ストライド4、`KHR_mesh_quantization`）で圧縮する。1頂点の法線が12→4バイトになる。
全頂点を復号して元の法線との角度を検査し、1.5°を超えれば失敗にする（実測の最大1.16°）。three 0.186の `GLTFLoader` は正規化int8を `InterleavedBufferAttribute` として読み、シェーダーでは従来どおりfloatの法線として扱う。

本体には適用しない：`refraction.ts` の `sliceUnderwater` などがJSで属性を作り直す。庭は水に届かず（水中の三角形があれば失敗扱い）、法線を読むのはシェーダーだけ。
位置の整数化（int16）はしない：ノード変換に逆量子化を載せるため、オブジェクト座標でノイズを評価するシダ（`noiseColor.ts`）の模様が変わる。

v11の元blend（`export-report.json` の入力と同じハッシュ）からBlenderで別出力先へ書き出し、**庭GLBだけ**差し替えた。同時に出た本体GLBは配信中のものと違う（温度計の数字にTEXCOORD_1が増え、画像のバイト列も違う）ため採用していない（原因は調べていない）。経緯は `compression-report.json` の `gardenReexport`。

## 結果

- 庭GLB：7,117,228→**5,979,340 bytes（−1.14MB、−16%）**。メッシュ・三角形・材質・ノードは同じ。
- GPUメモリ（`gpu-memory.e2e.ts`、1280×800・DPR1）：バッファ28.32→**22.92MiB**。合計は軽量129.7→124.3（−4.2%）、標準189.4→184.0（−2.9%）、高精細322.1→316.7MiB（−1.7%）。周回・再生成をまたいで同じ値。頂点の量は画素数によらない。
- 画像：Cycles 6視点×昼夕夜と水風呂12視点を、標準画質・DPR 1.5・PNGで変更後→変更前→変更前→変更後と撮った。同じ版の2回は一致（Cycles 01・04・05だけ従来どおり読み込み間でわずかに揺れる、平均ΔE 0.0003以下）。変更前に対するΔE76は平均0.0000〜0.076、ΔE>2の画素は0.038%以下（2回とも同じ値）。差は葉の輪郭・葉の上の孤立した画素に散らばり、目視では区別できない（[中庭・昼の拡大](crop-cycles-01-day.png)、上段が変更前・後、下段が差×8。画像はローカルのみ）。差には法線の量子化だけでなく、再書き出しによる位置のフィルターのゆらぎ（許容0.1mm）も含まれる。
