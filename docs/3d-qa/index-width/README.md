# 庭の32bitインデックスの内訳（2026-10-05、調査）

配信中の2つのGLBを `scripts/diagnose_glb_indices.mjs` で復号し、全インデックスの値・頂点範囲を検査した。配信物・製品コードは変更していない。

本体はすべて16bit。庭の32bitは4プリミティブだけで、最大インデックスは78,615・76,647・77,911・77,863。全頂点が使われており、型の置き換えだけでは16bitに収まらない。

三角形の順序を保ち、1バッチの固有頂点を65,535以下にする貪欲分割を見積もった（WebGL2の16bit primitive restart用の65,535は参照しない）。各プリミティブは2分割、重複頂点は各2個。位置12バイト・正規化法線4バイトを複製した場合の正味削減は合計932,992バイト（0.890MiB）。これは庭の法線8bit化で得た5.4MiBより小さい。

分割するとメッシュ／描画呼び出しが主描画で4個増える。影・鏡像でも追加の呼び出しを生む可能性がある。実際の分割・圧縮・ロード・GPU時間・画像比較は実施していないため、採用判断は保留する。転送量やドライバーの実確保量をこの見積もりから主張しない。これは最初の見積もり時点の記録。本体法線の採用済み検証は [本体属性](../body-attributes/README.md) を参照。

再実行：

```sh
node scripts/diagnose_glb_indices.mjs docs/3d-qa/index-width/values.json
```

[値](values.json)には入力とスクリプトのSHA-256、すべてのプリミティブの参照範囲と分割見積もりを記録する。復号失敗・想定外の型・範囲外インデックスは失敗にし、入力が実行中に変わらないことも検査する。見積もりは分割に伴う属性共有・描画順序への影響の検証に代わるものではない。

## 16bit分割候補の生成・ブラウザ比較（2026-10-05）

`make_garden_index_candidate.mjs` は配信中の庭GLBから32bitの4プリミティブだけを各2分割する。ノード・材質・三角形の順序を保持し、各三角形の参照先と全属性の復号後バイトを検査する。分割後の各バッチは65,535頂点以下、最大インデックス65,534。位置の境界を各バッチで再計算し、使わなくなったアクセサ・バッファを除く。配信物には書き込まない。

EXPONENTIAL／OCTAHEDRALを再量子化せず、フィルター適用前のバイトを分割して同じフィルターで再圧縮する。再復号後のバイトが元の頂点と一致することを全属性で検査する。初期のフィルターなし候補はGLBを519,624バイト増やしたため比較対象から外した。最終候補は5,979,340→5,983,996バイト（+4,656、+0.078%）。復号バッファの和は16,181,952→15,248,960バイト（−932,992、0.890MiB）、重複頂点は合計8個。ドライバーの実確保量ではない。

```sh
node scripts/make_garden_index_candidate.mjs /tmp/sauna-garden-uint16.glb docs/3d-qa/index-width/candidate.json
QA_GARDEN_MODEL=/tmp/sauna-garden-uint16.glb GARDEN_INDEX_REPEAT=4 bun run test:browser:gpu e2e/garden-indices.gpu.ts --reporter=json > /tmp/sauna-garden-indices-final.json
python3 scripts/summarize_garden_indices.py /tmp/sauna-garden-indices-final.json docs/3d-qa/index-width/candidate.json docs/3d-qa/index-width/browser.json
```

ブラウザテストは標準画質・1200×800・DPR1・動作抑制・固定解像度の3ステージ既定視点×昼夕夜を現行→候補→候補→現行で比べる。庭のHTTP応答だけを差し替え、取得回数・モデルのハッシュ・エラーなしを検査。WebGL割り当てのバッファ推定値、描画数、三角形数、PNGを記録する。GPU費用は描画のあるrAFを4回ずつ実行し、そのフレーム間隔の平均を4で割る。ANGLE Metalのクエリー値には待ち時間が混ざるため、クエリー値だけを描画費用やFPSとしない。撮影はTAAの静止判定を超える70フレーム後。

集計は4件の成功・再試行なし・ABBA順・画質・DPR・繰り返し数・9視点・入力ハッシュの一致・画像ハッシュを要求する。画像の再撮影差と候補との差は別に記録する。今回は既定視点の静止画と定常フレームの費用の比較であり、全周・実時間の見回し・動く波・読み込み速度・実機を検証するものではない。

### 結果・判断

Chrome 154.0.8037.97／macOSで最終候補の4件が成功（8.2分、36枚）。2組の候補−現行比較も、現行同士・候補同士の再撮影も9視点すべてRGB全画素一致した。候補の一覧を目視確認し、今回の既定視点に欠け・新しい境界の段はなかった。[ブラウザの値](browser.json) にPNGの画素比較と入力条件を保存する。

バッファ推定は全9条件で22,605,743→21,672,751バイト（−932,992）。テクスチャ・レンダーバッファは一致。描画呼び出しはサウナ138→142、水風呂129→133、外気浴83→87で各+4。描画三角形数は各条件で一致した。

4回描画の平均間隔÷4は現行約5.30〜11.63ms、候補約5.32〜11.72ms。対応する2組の比は0.9958〜1.0084（−0.42〜+0.84%）。改善とは判断しない。表示間隔による量子化・CPU／GPU待ちを含む診断値で、純粋なGPU処理時間や通常利用のFPSではない。定常視点なので影の更新と見回し中の鏡像更新の追加費用はこの測定に入らない。

判断：静止画とバッファ削減は確認できた候補として保持し、採用は保留する。約0.89MiBの削減に対し明確な描画速度改善はなく、採用前に全周・見回し中の鏡像更新／影更新・ロード費用を比べる。配信GLBと製品パイプラインは変更していない。フィルターなしの初期候補の4件も成功したが、最終判断の画像・費用には使っていない。

## 見回し中の鏡像更新・ロード費用（2026-10-05）

`garden-motion.gpu.ts` は標準画質・1200×800・DPR1・固定解像度・動作抑制で、3ステージ×昼夕夜の既定視点を現行→候補→候補→現行で測る。各条件で実際のマウス押下からドラッグを始め、描画のあるrAFを4回実行し、**各描画の後に1 CSS px（0.004rad）ずつ左右交互に動かす**（`gpu-timer.ts` の `suiAfterDraw`）。視点が毎回変わるので水面の鏡像は4回とも描き直され、TAAも動いている状態になる。見回しの予備測定（記録しない）の後、静止→見回しを各4秒測り、描画間隔の平均÷4を費用の診断値とする。

影マップは静的で、描き直すのは庭の追加時と画質変更時だけ（`lighting.ts` の `refreshShadows`／`setShadowSize`）。そこで各回の後に新しいページで6回読み込み（標準・昼・サウナ）、庭の段階（`data-garden-ms − data-load-ms`：取得・復号・コンパイル）と、庭を加えた最初のrAF（庭のバッファ転送と影マップの再描画を含む）のCPU時間・次のrAFまでの間隔を記録する。

```sh
node scripts/make_garden_index_candidate.mjs /tmp/sauna-garden-uint16.glb /tmp/sauna-garden-motion-candidate.json
QA_GARDEN_MODEL=/tmp/sauna-garden-uint16.glb bun run test:browser:gpu e2e/garden-motion.gpu.ts --reporter=json > /tmp/sauna-garden-motion.json
python3 scripts/summarize_garden_motion.py /tmp/sauna-garden-motion.json /tmp/sauna-garden-motion-candidate.json docs/3d-qa/index-width/motion.json
```

集計は4件の成功・再試行なし・ABBA順・9視点・画質とDPR・入力／候補ハッシュ・読み込み条件と、候補で主パスの呼び出しが+4であることを検査する。

### 結果

Chrome 154.0.8037.97／macOSで4件成功（14.3分）。候補のハッシュは前回と同じ。[全値](motion.json)。

| 比較 | 静止（候補÷現行） | 見回し（候補÷現行） |
| --- | ---: | ---: |
| 1組目（現行1→候補1） | 1.0011〜1.0202 | 0.9017〜1.0041 |
| 2組目（現行2→候補2） | 0.9948〜1.0304 | 0.9947〜1.0086 |

- 見回しの追加費用（見回し−静止）は、1組目の現行を除いてサウナ約1.8〜2.6ms、水風呂約1.4〜1.9ms、外気浴約0.0〜0.2ms（水面が視界外で鏡像を描かない）。1組目の現行（最初のページ）はサウナ・外気浴で追加費用が約0.2〜1.2ms大きく、見回しの0.90の比はこの立ち上がりの影響とみる。2組目の見回しは−0.5〜+0.9%。静止では候補がわずかに遅い側（最大+3.0%）に寄った。
- 鏡像パスの描画呼び出しも候補で+4（サウナ80→84、水風呂52→56）。三角形数は同じ。
- 読み込み（各版12回の中央値）：庭の段階147.5→149.5ms、庭を加えた最初のrAF 20.0→23.5ms（現行18.8〜33.5、候補19.6〜28.3ms）、続くrAFは両版とも約3〜4ms。分布は重なり、候補の短縮は見られない。

### 判断

**採用しない。** 推定0.89MiBのバッファ削減に対し、静止・見回し・読み込みのいずれも速くならず、主パス・鏡像パスの描画呼び出しが各+4、製品パイプラインに分割処理が加わる。候補生成・比較の仕組みは残し、メモリの厳しい実機で頂点バッファが問題になったときに再検討する。GPUだけの時間、ドライバーの実確保量、実時間の連続見回し、実機は検証していない。
