# 水の底面の反射の「傾けた4本の追跡」の費用の正体（2026-10-01、不採用3件・記録）

[コースティクスのセルのキャッシュ](../caustic-cells/README.md)の残件「DPR 1.5の水風呂の夕暮れ・夜の残り約2.5ms」のうち、水の底面の反射（`waterBottom.ts` の `suiBottomReflection`）を調べた。**製品コードの変更はない。** 3つの最適化を試したが、どれも採用基準に届かなかった。費用の帰属の誤りと、費用の性質（実行量ではなくコードの存在）が分かった。

条件：Chrome／ANGLE Metal（Apple M1 Max）、headless、`e2e/frame-cost.gpu.ts`、1200×800・動作抑制・標準画質・DPR 1.5、繰り返し2回のフレーム間隔（`intervalMs.mean`）。変種の節約量は直前・直後の製品との差（[cost.json](cost.json) の `lightCosts`）。

## 分かったこと

### 1. 前回の内訳の `cut-bump` は「バンプの追い直し」の費用ではなかった

前回の表は、傾けた4本の追跡（`cut-tilt`）が1.5〜1.8ms、揺らした追跡（`cut-bump`）が1.3〜1.6msとしていた。今回、2つの変種を加えた。実行されないがコードは残す `cut-bumpnever`（`if ( near && gl_FragCoord.x < - 1.0 )`）と、全画素で追い直す `cut-bumpall` である。

| 水風呂、DPR 1.5（ms、中央値） | 昼 | 夕暮れ | 夜 |
| --- | ---: | ---: | ---: |
| `cut-tilt`（4本の追跡と追い直しを外す） | 1.43 | 1.19 | 1.24 |
| `cut-bump`（`if ( false )`） | 1.16 | 1.06 | 1.09 |
| `cut-bumpnever`（コードは残し実行しない） | −0.06 | −0.07 | −0.07 |
| `cut-bumpall`（全画素で追い直す） | −3.4 | −3.4 | −3.2 |

- `cut-bumpnever` が製品と同じなので、追い直しのコードは存在するだけでは費用にならない。
- 近傍と判定される画素（追い直す画素）を色で塗ると、既定視点ではほぼ0で、見下ろしで灯りの像の縁に数画素幅の輪が出るだけだった（水風呂64視点で約32万画素、全体の0.5%）。
- `cut-bump` が1ms減らしたのは、`near` が使われなくなり、**コンパイラが4本の追跡ごと消した**ためである。費用の本体は、全画素で走る4本の追跡（約1.0〜1.2ms）だった。前回の表の「傾けた4本／揺らした追跡」は、どちらもほぼ同じものを測っている。
- 判定幅 `BUMP_REACH` を0.006から0.0045・0.003に狭めても、費用は変わらなかった（±0.1ms）。

### 2. 4本の追跡の費用は、実行量ではなくコードの存在から来る

追跡を省ける画素を前もって選ぶ判定（下記「不採用2・3」）を入れた版で、同じビルドの中で比べた（[bound-split.json](bound-split.json)、各2回）。

| 水風呂、DPR 1.5（ms） | 昼 | 夕暮れ | 夜 |
| --- | ---: | ---: | ---: |
| 常に4本を追跡（判定を外す、`maytrue`） | −0.05 | −0.13 | +0.02 |
| 常に省く（`mayfalse`、コンパイラが追跡を消す） | 1.04 | 0.99 | 1.03 |

- 判定は追跡する画素を水風呂64視点で44%減らしたのに、常に追跡する場合と費用が変わらない。省いた画素の分は速くならず、コードが消えたときだけ約1ms減る。
- PCSSで既に見ていた「実行されない分岐でも費用になる」（`src/components/3d/CLAUDE.md` の影のマスク）と同じ性質で、レジスタの割り当て（占有率）と考えられる。ただし、バンプの追い直しのように存在しても無料のコードもあり、事前には分からない。
- 同様に、側面に映るハイライトの経路（`suiWetImage` のループ）は、外すと1.15〜1.6ms減る（`cut-wetimage`）。実行しない変種（`cut-wetimagenever`）でも0.5ms減るので、残る0.6〜1.1msがコードの存在による分である。

## 不採用

### 不採用1：バンプの3点の格子ハッシュの共有

バンプの勾配は、高さを前進差分で3点（0.4mm刻み）評価し、それを3か所で行う。3点はほぼ同じ格子セルにあるので、セルの8角のハッシュを1回だけ計算し、隣のセルに入ったときだけその面の4つを足した。

- GPU上の一致：従来の3回評価との差は最大5.96e−8（値0.5付近の1ulp、コンパイラの演算の融合の違い）。勾配に換算すると相対6e−6。
- 費用（HEADと交互4組）：水風呂 1.004〜1.009倍（わずかに遅い）、サウナ・外気浴は不変。追い直す画素がほぼないので、効果がないのは当然だった（上記1）。

### 不採用2・3：4本の追跡の前の保守的な事前判定

基準の追跡の結果から、傾けた追跡で見える灯りが変わり得ない画素では4本を省く判定である。

- 灯りへの近さ：傾けた視線が出る範囲を円錐で見積もる。その太さは、底面での転向、波の曲率（法線の振れはその場所の最大傾きの2倍で頭打ち）、屈折による広がり `n cosθw / cosθa`、出口のずれから決める。この円錐が灯りの外接球に届かないこと。
- 経路：側面か水面かの選択が、傾けで変わり得ないこと。判定点から壁・水面までの距離で測る。変わり得る場合は、x・zを反転した向きでも灯りに届かないこと。
- 保守性：TSの参照実装で、10万標本のうち、傾けた追跡で灯りが変わる標本（8千以上）がすべて判定を通ることを確認した。画像では、水風呂・サウナ×昼・夕暮れ×8方位×4俯仰の128視点で、判定が省いた近傍の画素が0。陽性対照（近傍をすべて塗る）では32万画素を検出した。
- 費用（HEADと交互4組）：第1版（側面の境目は判定せず常に追跡）は水風呂 0.979〜0.990倍、第2版（境目でも反転を判定、追跡する画素−44%）は0.982〜0.995倍。サウナは0.996〜1.006倍。上記2のとおり、省いても速くならない。150行ほどのGLSL・TSに見合わないため不採用とした。

### 参考：灯りの構造体を保持して動的な添字をなくす（不採用）

側面の像のループは `spotLights[ suiSpot ]` を動的な添字で読む。展開済みのループで構造体ごと保持する形にすると、約0.3〜0.5ms遅くなった（同じ日のHEADの製品は夕暮れ約18.6ms、この版は約19.0ms）。なお、構造体への三項演算子はWebGL（ESSL）で禁止で、床のシェーダがコンパイルに失敗して描かれなくなる。最初の計測はこれで無効になった（水風呂の昼が8.33msに張り付く）。

## 次の候補

- 4本の追跡・側面の像の経路は、存在するだけで約1ms・0.6〜1.1msかかる。下げるには、コードを消す（画像が変わる）か、レジスタの使い方を変えて試すしかなく、効果は試すまで分からない。
- 画像を変えてよいなら、近傍判定を4本の追跡でなく安い判定（上記の円錐）だけにする手がある。追い直す画素が大きく増え（`cut-bumpall` は全画素で+3.4ms）、ほつれの範囲も変わるため、Cyclesとの比較が必要になる。

## 再実行

```sh
bun run build   # 変更前はHEADのworktree（node_modulesをリンクし、e2e/frame-cost.tsをコピー）
# bashで（zshは "$c" を分割しない）
FRAME_COST_DPR=1.5 FRAME_COST_REPEAT=2 \
  FRAME_COST_VARIANTS=warmup,product,cut-bumpnever,cut-bump,cut-wetimagenever,cut-wetimage,product \
  bunx playwright test --config playwright.gpu.config.ts e2e/frame-cost.gpu.ts --grep "frame cost" --reporter=json > split.json
python3 scripts/summarize_frame_cost.py --out docs/3d-qa/tilt-cost/cost.json \
  --runs shared-hash before=<4回> after=<4回> --runs bound-1 ... --runs bound-2 ... \
  --light-costs split1.json split2.json split3.json
```

`cost.json` の `lightCosts` の `cut-reach45`・`cut-reach30`（判定幅0.0045・0.003）は一時的な変種で、`frame-cost.ts` には残していない。`comparisons` の `shared-hash`・`bound-1`・`bound-2` は上記の不採用の版とHEADの交互計測。
